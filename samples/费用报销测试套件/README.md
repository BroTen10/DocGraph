# 费用报销端到端测试套件

用于手工验证 DocGraph 的完整链路：**规则导入 → 规则检查 → 新文件类型确认 → 构建图谱 →
上传待检查清单 → OCR 识别 → 选择已识别文档进行检查**。

全部文件均为**模拟数据**，不具备任何票据效力，仅用于功能测试。

## 目录

```
费用报销测试套件/
├── 费用报销规则描述文档.xlsx          ← 规则导入用（符合 templates/规则描述文档模板.xlsx 规范）
├── 01-合规报销_BX-2026-0312/          ← 应当全部通过
│   ├── BX-2026-0312_费用报销单.docx
│   ├── BX-2026-0312_增值税发票_1_航空客票.docx
│   ├── BX-2026-0312_增值税发票_2_住宿费.docx
│   └── BX-2026-0312_行程单.docx
└── 02-问题报销_BX-2026-0318/          ← 应当命中 5 条不通过
    ├── BX-2026-0318_费用报销单.docx
    └── BX-2026-0318_增值税发票_1_住宿费.docx
```

规则文件含「填写说明 / 场景与术语 / 规则清单」三张表，`场景 = expense`，
导入后生效配置应为 **通用规则解析契约 + 场景包：费用报销**（不是贸易场景包）。
规则清单 10 条，覆盖金额一致性、时间逻辑、齐套性、审批层级、形式审查与信息一致性。

## 操作步骤

### 1. 规则导入
「规则管理」→ **批量导入** → **文件导入** → 选择 `费用报销规则描述文档.xlsx` → 开始解析并导入。

- 业务场景下拉保持默认即可（文件内已声明 `场景 = expense`），**不要勾选 Skill**——
  勾了就进入「自定义场景」通道，不会加载费用报销场景包。
- 预期：解析 10 条、成功 10 条、跳过 0 条；提示已跳过 `填写说明` 工作表。

### 2. 规则检查
导入后部分规则可能落在「错误/警告」页签（解析器对"多张发票汇总""代垫费用例外"等
给出了 warning，系统按"待确认 + 已禁用"处理，这是设计行为，不是故障）。

**请在「规则列表」里确认并启用你需要参与检查的规则**——被禁用的规则不会进图谱。
最近一次实测：10 条中 7 条已确认启用，3 条（金额一致性 / 30 日间隔 / 申请人一致性）待确认。

### 3. 检查项确认（新增的一步）
导入时大模型会自己发明几个检查项（实测：`金额一致性`、`审批合规`、`形式审查`、`重复报销检查` 之类），
它们现在**不再直接长成规则列表里的新列**，而是登记为「待确认」：

- 进入 **「检查项」** 页 → 「待确认」页签，逐个处理：
  - 如果它就是已有检查项的另一种叫法 → 点 **合并**，并到 `信息准确性` / `基础判断` 等规范检查项上
    （合并会同步改写存量规则的引用，并把旧名保留为别名，后续导入自动归一）；
  - 如果确实是新的检查维度 → 点 **确认**，它才会成为规则矩阵里的独立一列。
- 未确认前，相关规则在「规则列表」里显示为 `未分类 + 待确认：xxx`。
- 导入结果里也会直接提示"发现 N 个新检查项"。

> 建议：测试时把 `金额一致性` 合并到 `信息准确性`、把 `形式审查` 合并到 `基础判断`，
> 并确认 `审批合规`（或直接合并到 `基础判断`），这样规则列表能收敛成 4 列规范检查项。

### 4. 新文件类型确认
「文档类型」页会新增 2 个待确认类型（`增值税发票` 会复用已有类型）：

| 类型 | 建议补充的字段（**重要**） |
|---|---|
| 报销单 | `报销金额`、`所属公司名称`、`申请人`、`费用发生人`、`费用发生日期`、`提交日期`、`费用类型` |
| 行程单 | `乘机人`、`合计金额` |

> ⚠️ **字段决定抽取模板**：OCR/字段抽取严格按 `key_fields` 执行
> （`ocr_service._llm_extract_fields_from_text`：有模板按模板提取）。
> 导入时预填的字段由大模型当次推断，**每次结果可能不同**（实测出现过只填了 `申请人` 的情况）。
> 如果不补全，报销金额、日期等取不到值，相关规则会以"无法核验"收场。
> 这一步正是"人工确认新类型"的意义所在。

确认后（`status = active`），文件名才能按类型自动归类。

### 5. 构建图谱
「图谱确认」→ **构建图谱** → 确认。

- 齐套性规则走程序化转换，印章类规则走程序化转换（MUST_STAMP），其余走大模型建图。
- 预期：7~10 条规则进入图谱（取决于第 2 步启用了多少条）。

### 6. 上传待检查清单
「文档上传」→ 选择一个文件夹的全部文件 → 开始上传。
**两个文件夹分两次上传**，每次上传 = 一个合同。

- 支持格式：PDF / PNG / JPG / DOCX（本套件为 DOCX，走"文本抽取 + 大模型字段提取"路径）。
- 文件类型自动归类依赖文件名关键词：含「增值税发票」→ 增值税发票；
  「报销单」「行程单」→ 动态注册表匹配（需先完成第 3 步）。

### 7. OCR 识别
在合同详情里点 **批量识别**，等待识别完成。预期字段抽取值：

| 单据 | 关键字段 |
|---|---|
| 01 报销单 | 报销金额 4860、提交日期 2026-03-09、费用发生日期 2026-03-05、所属公司名称 深圳市远航进出口有限公司 |
| 01 发票 ×2 | 价税合计 3200 / 1660，开票日期 03-06 / 03-08，购货方 深圳市远航进出口有限公司 |
| 01 行程单 | 乘机人 张伟 |
| 02 报销单 | 报销金额 5860、提交日期 2026-04-20 |
| 02 发票 | 价税合计 5000、开票日期 2026-04-25、无发票专用章 |

### 8. 执行检查
「审查执行」→ 选择合同 → 开始审查 → 「结果展示」查看结论。
建议两份合同各跑一次，对照上面「预期结果」表核对。

## 已知口径坑（测试时可能遇到，属系统行为而非数据问题）

1. **「基础判断」被一律当作印章检查**：`graph_builder_service._convert_stamp_rule` 对
   `检查类别 = 基础判断` 且有文件类型的规则，直接生成"必须盖章"节点，不看规则正文。
   因此本套件把"审批双签"规则归到「信息准确性」，避免被误判成"没盖章"。
   若你把审批类规则标成「基础判断」，会得到偏严的错误结论。
2. **规则分类由大模型判定**：同一份规则文件多次导入，个别规则的检查类别/待确认状态
   可能有差异。以导入结果为准。
3. **条件字段缺失 → 无法核验**：如果规则条件引用的字段不在该类型的 `key_fields` 里
   （例如"跨年度"需要的年度字段），结论会是"无法核验"而不是"通过/不通过"。
