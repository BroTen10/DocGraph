# 审查判定架构：统一判定（证据包 + 带引用判定 + 机器验证 + 绑定沉淀）

> 状态：已实现（批次 13）
> 相关代码：`backend/app/services/review_evidence.py`、`review_intent.py`、`review_judge.py`、
> `field_binding_service.py`；入口 `backend/app/services/review_service.py`（阶段 2.5）

## 1. 问题诊断：为什么"老是打补丁"

旧链路是**五段串联**，每段一个候选筛选器，每段都可能静默丢弃：

```
图引擎 → B-2 语义复核 → B-3 语义裁决 → B-4 全量复核 → 兜底强制收口
```

根因不是"引擎不够聪明"，而是**判定被拆进三个各自为政的层，层间只用"字符串相等"接头**：

```
OCR/抽取(LLM#1) ──字段名──┐
                          ├──► 精确字符串匹配 ==  ──►  Python 判定
规则解析(LLM#2) ──字段名──┘         ▲
                             唯一的接头：无语义、无协商、无反馈
```

抽取端看到的是**版面**（`报销金额（元）`、`审批签字`），规则端看到的是**规则文本**
（`报销金额`、`部门负责人签字`）。两个词表由两次独立 LLM 调用生成，用 `==` 连接，
不匹配就记 `field_missing` → 规则停在"无法核验"。

实测代价（验收案件 BX-2026-0312）：一次运行 13 条结果里有 **4 条"无法核验" + 1 条误判**，
全部来自这个接头；而单据内容完全可核验（报销金额 4860 元、部门负责人已签）。

同时暴露三类结构性问题：

| 问题 | 证据 |
|---|---|
| 规则形状装不进契约 | 10 条规则里 3 条 `structure` 为空（齐备/存在性/用印），各自需要一条专用代码路径 |
| 条件被静默丢弃 | 规则表有"触发条件=报销金额≥5000元"，图上 `condition: NULL`，于是"条件型要求"变成"金额 不小于 签字" |
| 参数解析了不生效 | `tolerance_params.time_days=30` 入库，比对函数从未使用 → 合规单据被判不通过 |

补丁为什么会无界：字段名空间是开放的（20 个类型 / 149 个字段名，还在长），
每遇到一个新说法就在接头两侧加一条特例（别名表、单位后缀表、角色词表、提示词规则…），
**特例数量随场景线性增长，且互相不知道对方存在**。

## 2. 新架构：一条判定路径 + 一个验证门 + 一个反馈环

```
        规则条款 + 结构化契约 + 图谱关系          单据 OCR 结果（字段 + 原文行 + 置信度）
                    │                                        │
                    ▼                                        ▼
        ┌───────────────────────┐              ┌───────────────────────────┐
        │ 意图编译 review_intent│              │ 证据包 review_evidence    │
        │ 条件/义务/例外/要找什么│              │ facts(key,value,raw,line) │
        │ + 确定性初判 prelim    │              │ + 字段索引 + 派生事实      │
        │ + 建模体检 warnings    │              └───────────────────────────┘
        └───────────┬───────────┘                          │
                    └──────────────┬───────────────────────┘
                                   ▼
                     ┌──────────────────────────────┐
                     │ 大模型判定 review_judge      │  必须输出：
                     │ 一条提示词，按批处理          │  verdict / condition_met
                     │                              │  checks（声明做过的比较）
                     │                              │  citations（逐字来自证据包）
                     │                              │  bindings（字段名等价）
                     └───────────┬──────────────────┘
                                 ▼
                     ┌──────────────────────────────┐
                     │ Python 验证门                 │  引用存在性 / 数值-日期重算 /
                     │ verify_verdict               │  结论自洽 / 置信度护栏
                     └───────┬──────────────┬───────┘
                        通过 │              │ 不通过（带失败原因重试，最多 2 次）
                             ▼              ▼
                  落库 + 引用留痕      保留确定性结论并标「需人工复核」
                             │        （本来就没结论的才落 unverifiable）
                             ▼
                  ┌──────────────────────────────┐
                  │ 绑定沉淀 field_bindings       │
                  │ 命中 N 次 → 自动升级为别名     │
                  │ 学到的签字角色映射回喂引擎      │
                  └──────────────────────────────┘
```

### 2.1 职责重新划分

| 能力 | 归属 | 理由 |
|---|---|---|
| 读单据、把规则语言绑到单据事实（指代/角色/单位/条件语义） | **大模型** | 语义绑定是它的强项，不该由字符串匹配承担 |
| 定位与范围（哪些单据、哪条规则适用、跨单据关系） | 图谱（检索 + 适用性） | 规则图谱仍是"规则管什么"的单一来源 |
| 算术、汇总、区间、存在性、去重、溯源 | **Python** | 可复现、可重算，审计只认这个 |
| 结论 | 大模型出，**Python 逐条验证后才落库** | "信但验"（trust but verify） |

### 2.2 大模型输出契约

```json
{"results": [{
  "intent_id": "R0016#存在性检查->报销单.财务负责人签字",
  "rule_id": "R0016",
  "verdict": "pass|fail|unverifiable",
  "condition_met": true,
  "reason": "…引用具体单据与字段值…",
  "confidence": 0.95,
  "checks": [
    {"op": "ge", "left": {"cite": "报销金额", "doc_type": "报销单"}, "right": 5000, "ok": true},
    {"op": "le", "left": {"date_diff": {"from": {"cite": "费用发生日期"}, "to": {"cite": "提交日期"}}},
     "right": 30, "ok": true},
    {"op": "eq", "left": {"cite": "has_stamp", "aggregate": "all"}, "right": true, "ok": true},
    {"op": "exists", "left": {"cite": "签字角色:财务负责人"}, "ok": false}
  ],
  "citations": [{"doc": "BX-2026-0318_费用报销单.docx", "key": "报销金额", "value": 5860.0}],
  "bindings": [{"rule_field": "报销金额", "doc_key": "报销金额（元）", "kind": "alias"}]
}]}
```

**checks 的语义是硬约定**：`ok=true` 表示"这条要求成立"。
因此 `pass` 不允许出现 `ok=false` 的 check，`fail` 至少要有一条 `ok=false` 的 check
（`fail_without_failing_check` / `pass_with_failing_check` 会被打回）。

### 2.3 验证门（判定正确性的最后防线）

| 检查 | 打回原因码 |
|---|---|
| 结论取值合法 | `verdict_invalid` |
| 置信度护栏（fail ≥0.8 / pass ≥0.6） | `fail_confidence_too_low` / `pass_confidence_too_low` |
| 条件与结论自洽（条件不成立必须是 pass） | `condition_not_met_but_verdict_not_pass` |
| checks 逐条按证据包重算 | `check_failed:check_recompute_mismatch` 等 |
| 结论与自身 checks 自洽 | `fail_without_failing_check` / `pass_with_failing_check` |
| citations 逐字存在（文件+字段+值） | `citation_invalid:…` |
| bindings 指向真实字段（非致命，丢弃并留痕） | `bindings_dropped` |

checks 支持的算子：`lt/le/gt/ge/eq/ne/contains/in/exists/absent`；
操作数支持：标量、`{cite, doc, doc_type, aggregate, index}`、
`{date_diff:{from,to}}`（日期间隔天数）；聚合支持 `sum/count/min/max/first/any/all`
（`all` 对布尔是"全部为真"，对文本是"多单取值一致"）。

### 2.4 确定性初判（prelim）与覆盖

- 图引擎的结论（`source=graph`）作为 `prelim` 进入判定项，大模型**可以参考也可以推翻**；
- 推翻时结果里留痕 `judge_decision = {from, to, kind: override|resolved, why}`；
- **验证门不通过时不允许把确定性的 pass/fail 降级成"无法核验"**：
  保留结论 + 标「需人工复核」+ 写入 `judge_rejected`（模型当时说了什么、为什么没过）；
  只有本来就没结论的条目才落 `unverifiable`。

这条规则很关键：它保证"大模型抖动"不会损失已经可复现的结论（历史上正是这么丢结论的）。

### 2.5 绑定沉淀（把补丁变成数据）

```
验证通过的判定
   ├─ bindings（模型显式声明）
   └─ 引用解析发现的等价（模型写"报销金额"，证据包实际命中"报销金额（元）"）
        ↓ field_bindings (doc_type, rule_field, doc_key, kind, evidence_count, status)
        ├─ 命中 ≥ review.binding_promote_threshold（默认 3）且无冲突
        │     → 自动写入 document_types.field_aliases（下次写时/读时直接命中）
        └─ role_signature 类 → 学到的"角色 → 签字栏"映射，回喂图引擎
```

实测：`所属公司名称 ← 所属公司`（增值税发票）在 6 次命中后自动升级为别名。
冲突（同一单据字段被映射到多个规则字段）不自动升级，留在 `observed` 等人工在
「文档类型」页处理。

## 3. 运行与运维

### 3.1 设置项

| 设置 | 默认 | 说明 |
|---|---|---|
| `review.judge_enabled` | true | 统一判定总开关；关闭则只保留确定性引擎结论（回滚开关） |
| `review.judge_override_deterministic` | true | 允许判定覆盖确定性结论；关闭则只判定"未结案"条目 |
| `review.binding_promote_threshold` | 3 | 绑定自动升级为别名的命中阈值 |
| `review.judge_system` | 内置 | 判定提示词（可在「系统设置」页改） |

### 3.2 指标

每次审查任务摘要里的 `summary.judge`：

```json
{"enabled": true, "items_total": 10, "items_sent": 10, "items_skipped": 0,
 "verified": 10, "overrides": 3, "created": 0, "retried": 2, "escalated": 0,
 "llm_error": 0, "citation_errors": 0, "recompute_errors": 2,
 "bindings_recorded": 1, "bindings_promoted": 1, "bindings_dropped": 0}
```

关注四个数：`escalated`（交人工率）、`citation_errors` / `recompute_errors`
（模型瞎说率，重试后收敛属正常）、`bindings_promoted`（学习速度）。
`escalated` 长期不为 0 时先看结果的 `judge_rejected`，那是模型当次的原始输出。

### 3.3 结果怎么读

- `detail.judge`：判定原文（reason / checks / citations / citation_resolution / modeling_warnings）；
- `detail.judge_decision`：与初判相比改了什么（`override` / `resolved`）；
- `detail.judge_challenged`：确定性结论被保留但被质疑（需人工确认）；
- `detail.judge_rejected`：验证门打回的原始判定；
- `detail.manual_review_required` / `manual_review_reason`：必须人工看的条目。

## 4. 扩展点

1. **新的判定算子/操作数**：加在 `review_evidence._CHECK_OPS` / `resolve_operand`，
   同步在 `review.judge_system` 提示词里登记（提示词是唯一需要"教模型"的地方）。
2. **新的义务类型**：`review_intent.OBLIGATION_KINDS` 加类型 → 图谱侧给出对应边
   （参考 `MUST_EXIST` 的：builder 转换 + neo4j_client 查询 + 引擎检查 + 意图编译四条）。
3. **新的规则形状**：先看能否用 `condition` + `assertion` / `requirement` 表达；
   不能表达时**不要**让 LLM 建图硬塞，而是补契约（见 `rule_import` 提示词 7.1~7.3），
   并在 `model_warnings` 里加对应的建模体检项。
4. **禁止**：再新增"哪些结果值得兜底"的筛选器。任何未结案结果都必须进判定
   （这是旧架构四个漏判点的来源）。

要求 20 条结论全对、`escalated == 0`、`verified + skipped == sent`。
