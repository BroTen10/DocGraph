# 泛化规则体系重构设计（回归最初设计目标）

> 日期：2026-08-02
> 状态：设计提案（未改代码）
> 范围：规则导入/表示、本体、审查执行、前端规则管理

---

## 1. 最初的设计目标（本次重构的不变式）

用户原始目标与 PRD（《基于知识图谱的自动文档审查智能体-PRD.md》）一致：

1. **导入任意人类语言描述的规则列表**（文档或文本，不要求规范性、不要求预定义文件类型/检查项）；
2. **大模型通过语义理解拆分出具体的文件处理规则**，规则只限定在文档的检查、核验、审查范围；
3. **规则以知识图谱（本体数据）形式保存**；
4. **审查阶段 = 大模型能力 + 知识图谱记载的规则信息结合**，对一批 OCR 识别后的文档做审核，发现不符合规则的点并提醒用户。

## 2. 现状与偏离分析

### 2.1 当前链路

```
规则文档/文本
  → LLM 解析（doc_type + check_category 双必填，"必须是给定枚举之一"）
  → rules 表（doc_type/check_category NOT NULL，枚举来自 constants.py 硬编码）
  → 人工确认/去重/冲突检测（去重按 (doc_type, check_category) 分组）
  → 图谱构建（齐套性→REQUIRED、印章→MUST_STAMP、structure→COMPARE_TO、其余→LLM 转图）
  → 审查（纯确定性引擎：Neo4j 三类关系 + Python 比对）
  → 结果（三态 + 严重度 + 证据链，模板化建议）
```

### 2.2 四个偏离点

| 层 | 偏离 | 证据 |
|---|---|---|
| 1. 规则表示层 | 每条规则被强制归入"文件类型 × 检查项"格子；为空直接丢弃 | `rule_import_service.py` `_SYSTEM_PROMPT`（"doc_type 必须是给定枚举之一"）、`_USER_PROMPT_TEMPLATE`（注入 constants 枚举）、校验处"文件类型/检查项为空则跳过"；`models/rule.py` 两字段 NOT NULL |
| 2. 本体层 | 类型/字段/检查项从代码常量出发，而非从规则文档涌现 | `constants.py` 硬编码 18 类文件类型、4 类检查项、`FIELD_TEMPLATES`、`STAMP_REQUIREMENTS`；`rule_sets` 创建时预置 `doc_types/check_categories`；OCR 字段提取只读 `FIELD_TEMPLATES`（`ocr_service.py:160`），未使用 `DocumentType.key_fields`；分类器同样依赖常量枚举 |
| 3. 审查执行层 | 审查 = 纯确定性引擎，无 LLM 参与；无 structure 的定性规则没有执行路径 | `graph_review_service.py`（全确定性）；`review_service.py` fallback 按 `(doc_type, check_category)` 索引规则；`suggestion_service.py` 模板化（注释写明"未来可扩展为 LLM"） |
| 4. UI 层 | 二维矩阵从"投影视图"变成"输入契约" | `RulesPage.tsx` `essentialMissingCells`（约 226 行）把"必备文档 × 全部检查项"无已确认规则的空格判为"必检"并置顶 Alert（约 986 行），红色"必检"格引导用户逐格手工补规则（645-716 行） |

### 2.3 根因

系统把"规则怎么展示/编排"（文件类型 × 检查项的格子）当成了"规则是什么"（语义单元）的前提条件。正确的方向相反：**格子是规则语义的投影，应该由规则推导出来，而不是规则入库的前提**。由此连锁产生：去重按格子分组导致同一规则换标签不复用（历史出现 220 条重复）；新客户/新规则文档必须先把类型和检查项定义好才能导入（泛化能力被锁死）；定性规则（"文件应清晰可辨""签字应与盖章一致"）无法表达；审查阶段大模型缺位，与最初目标第 4 条不符。

## 3. 目标架构

### 3.1 设计原则

1. **规则自描述**：`structure`（条件/断言/例外 + 聚合/角色/币别/单位/容差）是规则的核心；`doc_type`/`check_category` 降级为**派生标签**，可为空。
2. **本体涌现**：文件类型、字段、检查意图在导入时由 LLM 从规则文档中抽象出来，注册进 `DocumentType` 等本体存储；已注册的复用，新出现的登记待确认（现有 pending_review → analyze-sample 闭环补齐）。
3. **双引擎审查**：声明式确定性引擎负责可结构化表达的逻辑（数值/日期/聚合/齐套/印章）；LLM 语义审查负责定性规则与语义兜底；LLM 不污染确定性结论（低置信 → unverifiable + 人工确认）。
4. **矩阵只读投影**：前端矩阵由规则推导，空单元格表示"规则未提及"，不再强制补齐。

### 3.2 规则数据模型变化

```text
rules:
  doc_type        NOT NULL → nullable   # 主类型标签（派生），可为空
  check_category  NOT NULL → nullable   # 主检查意图标签（派生），可为空
  + scope          JSONB/null           # {"doc_types": [...]} 或 "ALL"（整批合同/全部文件）
  + intents        JSONB []             # 检查意图列表（可多条，如 时间逻辑+信息准确性）
  + provenance     JSONB                # 来源：source_file / chunk / 原文片段，用于追溯与幂等
  structure        JSONB                # 转正为核心字段：condition / assertion / exceptions
```

迁移策略：旧规则两标签保留（向后兼容），新导入允许空标签；矩阵投影对旧规则仍按格子显示。

### 3.3 导入管线（LLM 输出契约 v2）

提示词变化：**枚举从"必须"降为"已知类型建议"**——"若原文含义与已知类型一致则复用；若原文使用新表述/新类型，以原文为准提出名称并登记到 ontology"。

```json
{
  "rules": [
    {
      "rule_text": "付款水单日期不得早于收款水单日期",
      "structure": {
        "condition": null,
        "assertion": {
          "source": {"doc_type": "付款水单", "field": "付款日期", "aggregate": "ANY"},
          "operator": "时间不早于",
          "target": {"doc_type": "收款水单", "field": "收款日期", "aggregate": "ANY"}
        },
        "exceptions": []
      },
      "scope": {"doc_types": ["付款水单", "收款水单"], "intents": ["时间逻辑"]},
      "tolerance": {"time_days": 0, "allow_same_day": true},
      "confidence": 0.98
    }
  ],
  "ontology": {
    "doc_types": [
      {"name": "付款水单", "description": "银行付款回单/流水", "aliases": ["银行水单", "付款回单"]}
    ],
    "fields": [
      {"name": "付款日期", "doc_type": "付款水单", "unit": null, "currency": null}
    ],
    "check_intents": [{"name": "时间逻辑", "description": "单据时间先后与收付顺序校验"}]
  },
  "defects": []
}
```

处理链：文本预处理（Skill）→ LLM 解析（新契约）→ 字段映射/默认值（Skill）→ **本体注册**（ontology → DocumentType pending_review + 预填 key_fields）→ 去重（**改为规则集内按 structure+归一化文本语义去重，不再按格子分组**）→ 缺陷/冲突检测 → 入库。

### 3.4 图谱：三层结构（本体 + 规则 + 执行）

```text
本体层    (DocumentType)-[:HAS_FIELD]->(Field)   (CheckIntent)
规则层    (Rule)-[:APPLIES_TO]->(DocumentType)  (Rule)-[:CHECKS]->(CheckIntent)  (Rule)-[:INVOLVES]->(Field)
执行层    COMPARE_TO / REQUIRED / MUST_STAMP（保留现状，由 structure/scope 程序化派生）
```

本体层即"图谱记载的规则信息/本体数据"，审查时供 LLM 取上下文（类型别名、字段清单、业务含义），也供图谱页展示。

### 3.5 审查管线：双引擎

```text
OCR 文档 + 提取字段
  → 引擎 A（现有 graph_review_service，确定性）：
      COMPARE_TO/REQUIRED/MUST_STAMP → pass/fail/unverifiable + 证据链
  → 引擎 B（新增 llm_review_service）：
      无 structure 的定性规则 + 语义兜底（字段别名映射/字符串语义相等）
      输入：规则文本 + 本体上下文(KG) + 提取字段 + OCR 片段
      输出：{result, evidence, issue, suggestion, confidence}
  → 合并：ReviewResult 增加 source（graph|llm）、confidence；LLM 低置信 → unverifiable + 待人工确认
```

### 3.6 前端变化

- `RulesPage.tsx`：删除 `essentialMissingCells` 必检 Alert 与红色"必检"格逻辑；空单元格显示"规则未提及"（灰）或作为可选的"添加规则"入口（仅便利，不构成约束）。
- 矩阵行列来源：规则集已注册类型（来自导入，不再预置常量）+ 实际规则中的标签。
- 导入结果预览：新增"发现的新文档类型（待确认）/新检查意图/缺陷冲突"展示，确认后进入类型样本分析（现有 DocTypesPage/analyze-sample）。

## 4. 分阶段改造方案

### Phase A：解除"规则-格子"强绑定（最高杠杆）

- `models/rule.py`：`doc_type`/`check_category` 改 nullable；新增 `scope`/`intents`/`provenance`。
- `database.py`：迁移 SQL（ALTER + ADD COLUMN）。
- `schemas/rule.py`：`RuleBase` 两字段可选。
- `rule_import_service.py`：
  - `_SYSTEM_PROMPT` / `_USER_PROMPT_TEMPLATE` 改为 v2 契约（枚举降级为建议、输出 ontology、scope/intents）；
  - 校验放宽：两标签为空不丢弃，但 `rule_text`/`structure` 至少其一必须存在；
  - 去重改为规则集内按 `structure + 归一化 rule_text` 语义相似度（跨标签复用，修复重复根源）；
  - 注册新类型时预填 `DocumentType.key_fields`（从 ontology.fields 推导）。
- `RulesPage.tsx`：移除必检 Alert/必检格；矩阵投影化。
- **验证**：用一份全新客户规则文档（含未注册类型/新检查意图）导入，应能全部入库并生成 pending_review 类型，无需任何人工预定义。

### Phase B：本体涌现闭环（消除硬编码对泛化的隐性限制）

- `constants.py`：保留为**种子数据/兜底**，不再作为唯一枚举源。
- `ocr_service.py`：`field_template` 改为 `DocumentType.key_fields` 优先 + `FIELD_TEMPLATES` 兜底；无模板时走自由提取（已实现）。
- `file_classifier.py`：类型清单从 `DocumentType` 动态读取。
- `rule_sets`：新规则集 `doc_types/check_categories` 初始为空，由导入逐步积累（对齐 07-27 需求："对不同的规则集根本不要有预设值"）。
- `doc_types.py`：已有 analyze-sample/detect-from-rules 保留，补齐字段模板回填。

### Phase C：双引擎审查（对齐目标第 4 条）

- 新增 `llm_review_service.py`：无 structure 规则 + 语义兜底审查。
- `review_service.py`：`_run_review_pipeline` 在图引擎结果后追加引擎 B，合并结果（`source`/`confidence`）。
- `suggestion_service.py`：可选接入 LLM 生成建议（以证据链为上下文）。
- 前端结果页：展示结果来源与置信度标识。
- **护栏**：LLM 审查低置信一律 `unverifiable` + 人工确认，不允许直接 fail（防幻觉污染结论）。

### Phase D：图谱本体化（可选但推荐）

- `graph_builder_service.py`：写图时增加 `DocumentType`/`CheckIntent`/`Rule` 本体节点与 `APPLIES_TO`/`CHECKS`/`INVOLVES` 边（与执行边同 graph_id）。
- `neo4j_client.py`：本体查询接口（类型别名/字段/业务含义）。
- `GraphPage`：按"本体-规则-执行"三层展示。

### Phase E：回归与验收

- 新流程验收：任意规则文档 → 导入（新类型/意图自动发现）→ 类型样本分析 → 建图 → 双引擎审查 → 问题提醒 → 状态闭环。
- 回归：现有 24HCSP012260253 验收用例（acceptance_run.py）继续全绿；旧规则（带标签）不受影响。

## 5. 兼容性与风险

| 风险 | 应对 |
|---|---|
| 精度 vs 泛化 | 确定性引擎保持权威；LLM 只补充定性/语义场景，低置信 → unverifiable + 人工确认（三态机制即护栏） |
| 旧数据/旧规则 | 标签字段保留并向后兼容；矩阵对旧规则仍按格子显示 |
| LLM 审查延迟/成本 | 仅对无 structure 规则执行（数量通常少），或异步执行 |
| 新类型字段提取冷启动 | ontology.fields 预填 key_fields + 自由提取兜底（已实现） |
| 去重语义化误伤 | 相似度阈值 + structure 归一化比对，保留合并差异字段（沿用 `_merge_into_existing`） |
| 图谱重构建兼容 | 本体节点与执行边同 graph_id，旧图清理逻辑不变 |

## 6. 一句话结论

把"文件类型 × 检查项"从**规则入库的必填前提**降级为**规则语义的派生投影**，让本体从规则文档中涌现，让审查变成"确定性引擎 + LLM 语义审查"双引擎——这是回归最初设计目标的三个支点。
