# 贸易合同规则拆解与解析 Skill 设计

## 1. 结论

这份文档最合适的系统表示不是“61 行 = 61 条规则”，也不是“每个单元格 = 一条规则”，而是：

```text
客户规则表
  → 61 个规则族（贸易类型 × 模式 × 过程文件）
  → 每个规则族拆成多个原子判定
  → 条件/例外/场景作为上下文随判定保留
  → 可确定性执行的进入图谱结构，其余进入 LLM 语义审查
```

可直接粘贴到 DocGraph“规则解析 → Skill 内容”的成品是
[rule_parse_skill_贸易合同校验_系统对齐版.yaml](rule_parse_skill_贸易合同校验_系统对齐版.yaml)。

## 2. 原文结构

附件 PDF 共 4 页，内容源自一张明细表：

- 第 1 行：抽检合同清单以附件入系统，用合同号匹配资料。
- 第 2 行：根据合同号抓取 N9B 系统内容，与单据匹配。
- 第 3 行：客户回签文件用印与协议签署印章一致，不一致时查备案印章说明。
- 第 4 行：表头。
- 第 5-65 行：61 个规则族。

同版明细表的规则族分布为：

| 贸易类型 | 模式 | 规则族数 | 同版明细表数据行 |
| --- | --- | ---: | --- |
| 出口 | 代理（退税） | 8 | 5-12 |
| 出口 | 代理（不退税） | 3 | 13-15 |
| 出口 | 自营 | 9 | 16-24 |
| 进口 | 代理 | 8 | 25-32 |
| 进口 | 自营 | 9 | 33-41 |
| 转口 | 代理 | 8 | 42-49 |
| 转口 | 自营 | 9 | 50-58 |
| 内贸 | 自营 | 7 | 59-65 |
| **合计** |  | **61** | **5-65** |

表的四列检查目的分别是：

| 原表列 | 系统归属 | 拆解方式 |
| --- | --- | --- |
| 强控是否必备 | 齐套性 | 单个无条件必备用 `REQUIRED`；条件必备和组合齐套走语义审查 |
| 不看单据内容，单据本身基础判断 | 基础判断 | 用印、回签版本、正本、格式、单据关联分别成条 |
| 判断单据信息是否准确 | 信息准确性 | 每字段比较、系统内容比对、主体一致性分别成条 |
| 时间逻辑 | 时间逻辑 | 每对时间锚点一条，保持原文方向 |

## 3. “最佳拆解”的判断标准

最佳粒度不是越细越好，而是“一个失败原因可被独立定位”。采用以下边界：

### 3.1 应拆

- 原单元格中的 1、2、3 等独立编号，各成一条。
- 同一句列举多个字段，并对每个字段分别做相等或大小比较，各成一条。
- 同一句同时要求“存在”“盖章”“正本扫描”“不得可编辑”，因证据不同，分别成条。
- 一个日期断言含多个锚点，逐对拆分。
- “任一运输单据 + 货物签收单可替代”“委托采购确认单 + 采购订单二选一”等组合中，若组内每个文件还各有独立数据或时间检查，这些数据/时间检查另行拆分。

### 3.2 不应拆

- “快递单/海运提单/空运提单/铁路运单任一可满足”，是一个组合齐套规则。
- “运输单据 + 货物签收单，或派车单（公路运输）+ 货物签收单”，是一个 any_of(组合) 规则。
- “出入仓文件和派车单至少得 1 样”，是一个至少其一规则。
- 例外必须与其主规则一起保存，不能把“税款除外”拆成一条与收付款时间无关的独立规则。
- 同一个存在性要求中列出的一组固定字段，可保持为一条字段完整性规则；只有其中字段另做相等/大小比较时才拆。

### 3.3 示例

原句：

> 报关单与委托出口确认单信息比对，产品名称、规格型号一致，数量、金额不可大于委托出口确认单。

合适拆法：

1. 报关单产品名称应与委托出口确认单产品名称一致。
2. 报关单规格型号应与委托出口确认单规格型号一致。
3. 报关单数量应不大于委托出口确认单数量。
4. 报关单金额应不大于委托出口确认单金额。

原句：

> 快递单/海运提单/空运提单/铁路运单中一个文件有提供就 OK……或派车单（公路运输）+货物签收单也可以。

齐套部分必须保持一条：

> 在出口-代理（退税）场景，运输资料应满足以下任一组合：快递单/海运提单/空运提单/铁路运单；上述任一运输单据加货物签收单；派车单（公路运输）加货物签收单。

该组合内部若另有“所有文件为用印正本扫描件”或“签收单收货方为订单客户”，应另拆形式检查和信息准确性规则。

## 4. 场景、条件与例外

### 4.1 场景必须进入规则文本和 condition

当前 Skill 编译会保留 `scope.doc_types` 和 `scope.intents`，但会丢弃自定义的 `trade_type`、`mode` 等 scope 键。因此不能写：

```yaml
scope:
  trade_type: 出口
  mode: 代理（退税）
  doc_types: [代理协议]
```

应写为：

```yaml
rule_text: 在出口-代理（退税）场景，代理协议应为必备文件。
scope:
  doc_types: [代理协议]
  intents: [齐套性]
structure:
  condition:
    text: 贸易类型=出口；模式=代理（退税）
```

场景不是可从文档字段直接求值的条件，`field/operator/value` 留空，避免模型臆造求值字段。

### 4.2 条件齐套不能直接生成普通 REQUIRED

当前图谱的 REQUIRED 检查只按 `doc_type` 判断文件是否存在，不执行 `structure.condition`。如果把“发货单仓库点选仓库时才要求出入仓单”解析成：

```yaml
doc_type: 出入仓单
check_category: 齐套性
```

则无论仓库选项是否开启，审查都会要求出入仓单，产生稳定误报。

本 Skill 的处理策略是：

- 无条件、单一文件必备：填写 `doc_type`，生成普通 REQUIRED。
- 条件必备、任一组合、至少其一：不填单一 `doc_type`，在 `scope.doc_types` 列候选文件，在 `rule_text` 与 `structure.condition.text` 保留触发条件。图谱会跳过这类无单一文件类型的齐套规则，LLM 语义审查会接手。

这是当前系统能力下的正确降级，不是解析遗漏。

同样的限制也作用于字段比对：只要规则同时有 `structure.condition` 和
`structure.assertion`，图谱会先尝试执行 condition。纯文本场景条件无法从
source 文档字段求值时会返回 `unverifiable`，再进入 LLM 裁决。因此如果要求
确定性执行，应把贸易类型/模式做成独立的规则集上下文或可求值字段；在一个混合
场景规则集中，提示词能做的是保留场景，不能修复引擎缺少场景分派的问题。

### 4.3 例外必须附着在主规则上

例如进口代理先收后付：

```yaml
rule_text: 在进口-代理场景，除税款外，收款水单到账时间应早于付款水单付款时间。
structure:
  condition:
    text: 贸易类型=进口；模式=代理
  assertion:
    source:
      doc_type: 收款水单
      field: 日期
    operator: 时间早于
    target:
      doc_type: 付款水单
      field: 日期
  exceptions:
    - text: 税款除外
      reason: 进口代理税款的付款不要求先收后付
```

## 5. 系统字段映射与限制

### 5.1 当前真正生效的能力

| Skill 配置 | 当前实际行为 |
| --- | --- |
| `prompt_instructions` | 追加到规则解析 System Prompt，是核心行为控制面 |
| `field_mappings` | 只对规则顶层字符串字段做精确值映射 |
| `defaults.priority` | 按 `check_category` 填充优先 |
| `defaults.tolerance` | 为缺失容差填默认值 |
| `text_preprocessing` | 仅当 `type: replace` 时执行正则替换 |
| `domain_context` | 作为术语和常见模式追加到 System Prompt |
| `term_normalization` | 对最终 `rule_text` 做朴素字符串替换 |
| `validations` | 当前导入链路声明但未实际执行 |

因此成品 Skill 将关键约束放进 `prompt_instructions`，没有依赖未执行的 `validations`。

### 5.2 当前 YAML 模板中的风险

- 模板写 `type: regex`，编译器只执行 `type: replace`，该预处理会被静默忽略。
- `field_mappings.severity` 不会进入规则模型，因为规则没有顶层 `severity` 字段。
- `term_normalization` 是全局 `str.replace`。把“委托出口代理订单”替换为“委托出口确认单”会把原文括号中的替代名称改成重复文本，因此成品 Skill 故意留空术语表。
- 内置默认金额容差是 5%、重量容差是 0.5kg；客户原文未给容差，成品 Skill 将其严格覆盖为 0。

### 5.3 需要平台后续补齐的能力

这些不是提示词能彻底解决的问题：

1. REQUIRED 关系需要支持 `condition` 与 any_of/at_least_one 组合。
2. 需要执行 `validations`，否则其错误配置不会被发现。
3. 应统一预处理类型名为 `replace`，或真正支持 `regex`。
4. 规则模型需要正式的审查策略字段，例如 `hard_fail / manual_review / advisory`，当前不能靠顶层 `severity`。
5. PDF 导入应保留页、行和合并单元格来源；当前只有 Excel 会生成 `[SOURCE_ROW=...]`。
6. 当前 PDF 提取先追加表格文本、再追加版面文本，容易重复；生产导入这份表格应优先使用同版 `.xlsx`，以保留 61 个行级来源并正确展开合并单元格。
7. 图谱 MUST_STAMP 只能验证“是否有印章”，不能验证“是否是指定主体的印章”；指定用印方需要 OCR 印章主体信息与更细的图谱关系。
8. 组合齐套可能需要引用多个来源行；当前 `source_ref` 只有单个字符串。生产导入应增加 `source_refs` 或 `group_id`，同时保留每个来源行的覆盖记录。

因此成品 Skill 只把“任意印章是否存在”交给 MUST_STAMP。双方回签、指定主体
用印、印章与备案印章一致、正本/版本/可编辑性等检查保持为 LLM 语义规则，避免
确定性引擎给出看似已覆盖、实际检查不足的结论。

对于跨行组合，由于用户要求不得跨 `[SOURCE_ROW]` 合并，成品 Skill 采用
“行身份优先”的降级方案：逐行生成带分支条件的规则，并在每条规则文本中保留
完整组合语义。只有没有行级来源的 PDF 文本，才可以把同一单元格内的 any_of
保持成一条组合规则。长期应由平台提供真正的多来源规则组。

## 6. 已固化的重点业务判断

- 代理与自营使用不同的数量/金额基准。
- 退税与不退税的出口代理拥有不同的后续时间链。
- 出口运输与进口运输的时间方向存在相反规则。
- 大合同分批导致的数量差异不是直接失败，原文要求提示人工确认。
- 香港仓集拼快进快出可只有入仓文件。
- 第三方来款说明、协议备案其他印章说明属于例外依据。
- “入仓单据时间不能早于出仓时间”按原文保留，同时标记方向不确定，避免提示词擅自改成业务常识。

## 7. 使用方式

1. 在规则集页面进入“Skill”。
2. 新建 Skill，名称建议“贸易合同过程文件校验-系统对齐版”。
3. 将 YAML 文件全部内容粘贴到 Skill 内容。
4. 保存并启用；若默认 Skill 中的冲突指令仍生效，建议停用不必要的默认纠偏项，或在本次导入时只选择此 Skill。
5. 正式导入本规则表时优先上传同版 `.xlsx`，完成源行覆盖率检查后，再用 PDF 做一次回归，比较两边的规则族覆盖率。
