# 规则生命周期闭环与人工修正回灌

> 基线约束见 [项目基线-智能优先原则](项目基线-智能优先原则.md)：
> 规则引擎保留（速度与准确性），要消灭的是**人工维护规则**；
> 人工只在 **LLM 判不了**时介入，且修正必须沉淀回数据、由模型复用。

## 1. 闭环长什么样

```
自然语言规则文档
   → LLM 拆分（解析 Skill / 场景知识包 / 历史人工修正）
   → 冲突与缺陷检查 + 警告
   → 人工只修 LLM 判不了的部分  ──┐
   → 修正沉淀为数据（本文件第 2 节）│
   → 确定性引擎按规则数据执行       │
   → 审查判定（LLM 主判 + 机器验证）│
   → 人工纠正判错的结论 ───────────┘
        ↑ 回灌进提示词，同一类问题不再找人第二次
```

判断闭环是否有效的唯一指标：**同一类修正是否出现第二次**。
每次修正都写成一条数据（账本行），重复出现时 `hit_count` 累加——它加一，就说明回灌没生效。

## 2. 已落地：人工修正账本（`llm_corrections`）

- 表：`llm_corrections`（租户级）。字段：`scope / field / before / after / context /
  doc_type / hit_count / created_by / first_seen / last_seen`；
  同类修正按 `signature = sha1(scope|rule_set|field|before|after)` 去重累加。
- 服务：[correction_ledger.py](../backend/app/services/correction_ledger.py)
  - `record_correction` / `record_field_changes`：通用记账（无实际变化不记）；
  - `corrections_digest`：给**规则解析**提示词用的清单（语义字段、命中优先、字符预算裁剪）；
  - `judge_corrections_digest`：给**统一判定**提示词用的人工改判清单。

### 2.1 三个写入点

| 场景 | scope | 触发 | 写回哪里 |
| --- | --- | --- | --- |
| 规则页编辑规则字段 | `rule_edit` | `PUT /api/rules/{id}` | PG 规则数据（本次编辑）+ 账本 |
| 图谱页编辑边属性 | `graph_edit` | `PUT /api/rules/graph/confirm` | **写回 PG 规则数据**（图是派生视图）+ 账本 |
| 人工纠正判定结论 | `review_judge` | `PATCH /api/reviews/results/{id}/status`（`result` 字段） | 审查结果（留痕 `detail.human_override`）+ 账本 |
| 解析失败/跳过（LLM 判不了） | — | 导入结束自动留档 | `rule_import_runs`（界面「导入记录」可见，人工据此修文档或固化经验） |

### 2.2 两个回灌点（数据 → 模型）

- **规则解析**：`rule_import_service._with_correction_digest` 把
  「本租户历史人工修正」追加到解析系统提示词；
- **统一判定**：`review_judge.judge_system_prompt` 把「人工纠正过的判定」追加到判定系统提示词。

两者都是**数据注入**：Python 里不为任何一种情形写死判定分支。

## 3. 尚未闭环的缺口（按优先级）

1. **冲突/缺陷处理结果回灌**：`resolution` 只留在原地，冲突原因没有进账本；
2. **图谱删除操作**（`delete_node` / `delete_edge`）尚未投影到规则数据（当前只告警）；
3. **字段绑定冲突**（同一单据字段映射到多个规则字段）缺人工确认接口，
   判定架构文档声明"在文档类型页处理"，实现缺失；
4. **回灌强度**：同一条修正反复出现（`hit_count` 持续增长）说明回灌文字不够权威或不够具体，
   需要按实测迭代措辞（见第 4 节的实测记录）。

## 3.1 已闭环：解析失败留档，"LLM 判不了"看得见

导入进度与解析错误此前只在进程内存，重启即丢，人工无从下手。现在：

- 表 `rule_import_runs`（租户级）：状态 / 计数 / **未解析条目与原因** / 警告 / 任务级错误 / 起止时间；
- 落档时机：`create_task` 与**状态变化**、终态时写一次（进度类高频更新只留在内存，不把 DB 写爆）；
  留档失败只记日志，绝不影响导入本身；
- 接口：`GET /api/rules/import-runs?rule_set_id=…`（`rules.view`）；
  实时进度仍走 `GET /api/rules/import-tasks/{task_id}`；
- 界面：「规则」页 → **导入记录**：状态、导入/未解析条数，展开行直接列出"大模型没解析出来的部分与原因"。

## 3.2 已闭环：经验指令由 LLM 归并（人只做修正）

经验指令是"只增不减"的：修正越多、提示词越长、越容易自相矛盾。现在由模型维护：

- 服务：`rule_parse_skill_service.consolidate_experience_skill`
  —— 输入「现有指令 + 人工修正账本」，输出一份去重、有上限（默认 20 条 / 每条 200 字）、
  按重要性排序的指令清单，**替换**而不是追加 `prompt_instructions`；
- 接口：`POST /api/rule-sets/{id}/skills/consolidate`（`rules.manage`）；
- 界面：「规则解析 Skill」页 → **AI 归并经验**；
- 模型不可用或输出不可用时**经验保持原样**（返回 400 说明原因），不会把已有经验改坏。

## 4. 怎么验证

```bash
# 账本 + 回灌 + 经验归并（无需 LLM）
TEST_DATABASE_URL=... pytest tests/test_correction_ledger.py \
  tests/test_judge_correction_feedback.py tests/test_graph_edit_writeback.py \
  tests/test_skill_consolidation.py
```

端到端验证（需要 LLM，脚本自建临时规则集、跑完清理）：

```bash
cd backend && .venv/bin/python ../tests/rule_loop_live.py
```

它做的是 A/B 对照：同一段规则文本解析两次，中间只有一处差异——**走真实入口**
（`rule_service.update_rule`，与 `PUT /api/rules/{id}` 同一路径）把规则的检查项改一次。
第一次模型给出 `信息准确性`，修正入库后第二次按人工口径给出 `基础判断` → 闭环成立
（人工修正 → 账本 → 提示词回灌 → 模型改变输出，全程没有改一行代码/配置）。

> 注意：**回灌的文字必须带"权威性 + 适用范围"**，否则模型会按语义否掉修正（实测：
> 只写"把 A 改为 B"时模型坚持原判；补上"本租户人工裁定，优先级高于默认习惯"与
> "适用示例：<规则原文摘要>"后才采纳）。同一类修正重复出现（hit_count 累加）也是
> 回灌强度不足的信号。
