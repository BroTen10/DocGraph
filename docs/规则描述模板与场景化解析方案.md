## 0. 结论先行

1. **原始规则文档的形态几乎线性决定拆解质量**，原因不在"大模型不行"，而在于当前链路的 6 个确定性机制（分段长度、逐行来源、去重身份、合并单元格继承、冲突分组、容差默认值）都直接读输入文档的结构。原文缺什么，系统就只能猜什么——而系统对"猜"的处理方式是**降级为待确认 + 禁用**，于是表现为"慢、漏、重、冲突多"。
2. 因此推荐**结构化模板**而不是"写得更好的自然语言"：把适用范围、触发条件、比较关系、容差、例外这 5 件事从"让模型猜"变成"客户填写"。模板不是文档规范，而是**把 Skill 里的隐性知识显性化到输入文档中**。
3. 关于 Skill：**不建议删除 Skill 机制，但必须改变它承载的内容**。Skill 应该是"项目级纠偏覆盖"，不应该承载"贸易单证领域知识"。领域知识应下沉为**场景知识包（scenario pack，一个 YAML 文件）**，由导入文件/规则集声明的**场景键**选择。这样：
   - 接入费用报销、供应商审查 = 新增一个 YAML，**零代码改动**；
   - 不需要"每个场景开发一个解析 skill"这种把数据写成代码的做法；
   - 通用解析契约（原子性、来源行、条件/例外归属、比较方向、模板列映射）与领域无关，全场景共享。
4. 本次已落地 4 项改动：**场景知识包分层**、**模板识别与文档级声明（场景 + 术语）**、**去重误合并修复**、**非规则工作表跳过**。其中"去重误合并"是本次实测发现的真实缺陷（见 §3），它会直接吃掉模板带来的收益。

## 1. 当前"上传文件 → 拆解规则"是怎么做的

### 1.1 全链路

```text
上传文件（PDF/XLSX/DOCX/MD/TXT）
  └─ 提取文本                                    rule_document_import_service.extract_document_from_file
       ├─ Excel：展开合并单元格 → 识别表头 → 逐行输出 [SOURCE_ROW=Sheet!行号] {列名:值,...}
       ├─ PDF  ：pdfplumber 先表格后版面（可能重复）；<50 字符时 PyMuPDF 兜底
       └─ DOCX/MD/TXT：段落/表格/原文
  └─ 分段（>2000 字符切块）                       rule_import_service._split_text
  └─ 装配提示词                                   编译场景知识包 → System Prompt
       System = 基础契约(prompt_templates.RULE_IMPORT_SYSTEM) + 通用契约包 + 场景包 + 规则集 Skill + 表格行约束
       User   = 本次导入声明(场景/术语) + 已知类型 + 已知检查项 + 本段原文
  └─ LLM 解析（temperature=0.1, max_tokens=8192, 关思考）
       输出 { rules[], ontology{}, defects[] }
  └─ 后处理（Skill）：文本预处理 → 字段映射 → 默认值 → 术语归一
  └─ 逐条入库                                      rule_import_service.import_rules_from_text
       ├─ 派生标签 doc_type/check_category（可空）
       ├─ 归一 scope/structure/字段名（别名表 + 注册表）
       ├─ 规则集内语义去重合并（_find_similar_rule）
       ├─ 缺陷分类 → 无实质缺陷自动确认启用；有缺陷 → 待确认 + 禁用
       └─ 来源行覆盖率校验（_compute_source_coverage）
  └─ 冲突检测（LLM，按 doc_type×check_category 分组两两比对）rule_conflict_detector
```

### 1.2 六个"读文档结构"的确定性机制

| # | 机制 | 位置 | 对输入文档的要求 |
|---|---|---|---|
| 1 | 分段阈值 2000 字符，表格行整行不拆 | `rule_import_service.py:64,67` | 一行别太长；一行一条规则，避免跨段 |
| 2 | 每行 `[SOURCE_ROW=...]` 独立候选 + 覆盖率校验 | `rule_document_import_service.py:423`、`rule_import_service.py:667` | 用 Excel；规则清单表要逐行填写 |
| 3 | 合并单元格值继承到每一行 | `_expand_sheet_merged_cells` | 纵向合并可用，但**不能靠空值表达"同上"** |
| 4 | 去重身份 = scope + condition + exceptions，文本相似度 ≥0.75 | `rule_import_service.py:205,271` | 适用对象/条件/例外必须逐行写全 |
| 5 | 冲突检测按 `(doc_type, check_category)` 分组 | `rule_conflict_detector.py:289-293` | 检查类别留空会让所有规则挤进同一组 |
| 6 | 容差默认 0（严格）、无阈值即 `missing_value` 缺陷 | 通用契约包 `defaults.tolerance` | 需要容差必须显式写 |

**一句话**：系统不是"理解能力不足"，而是"猜不到就降级"。模板的作用就是把 4 个关键字段（适用对象、触发条件、比较关系、容差/例外）从"猜"变成"抄"。

### 1.3 速度由什么决定（客户最关心的"更快"）

- 解析按 **2000 字符/段**切分，每段一次 LLM 调用（`_MAX_CHUNK_CHARS`，`rule_import_service.py:64`）；模板每行 JSON 约 300~400 字符，即**每次调用约解析 5 条规则**。61 行的规则表 ≈ 13 次调用，这是导入耗时的主要来源。
- 单个 `[SOURCE_ROW=...]` 行**永远不会被切断**（`_split_text` 对模板行整行保留），所以模板行再长也不会破坏解析，只会让该段变长。
- 因此"更快"的三个可行杠杆：① 模板行保持简短（去掉冗余描述）；② 提高分段阈值（需确认输出不超过 `max_tokens=8192`，见 §8）；③ 对标准模板列做**直接映射**、跳过 LLM（见 §8）。
- 反过来，自然语言长段落会被切得很碎，且切点常在规则中间 → 调用次数多 + 拆解质量差。这是模板相对自然语言最直接的收益。

## 2. 原始文档质量差时，具体会发生什么

| 原文形态 | 链路行为 | 客户感知 |
|---|---|---|
| 一行里混 4 个字段比较 | 依赖模型拆行；漏拆则一失败点无法独立定位 | "明明写了却没查出来" |
| "金额应一致"没写和谁比 | `structure.assertion` 缺 target → 剔除断言 + `incomplete_condition` 缺陷 → 待确认 + 禁用 | "导进来是灰的" |
| "相关日期""有关部门" | `ambiguous_reference` 缺陷 | 一堆待确认 |
| 金额/日期比对没写容差 | 容差 0 + `missing_value` 缺陷；或严格比对产生误报 | "误报太多" |
| 多条规则文本相似但适用对象不同 | 若 scope/condition 也不同 → 不合并（正确）；若都没写 → 同身份 → 可能被合并 | "重复的没合并 / 不同的被合并" |
| 大段制度原文直接粘贴 | 过程说明、采集方式、下步计划都会变成规则候选 | 噪声规则 |
| "任一即可/二选一"拆成多行 | 变成多条强制必备 → 稳定误报 | "明明提供了还说缺" |
| PDF 表格导入 | 无 `[SOURCE_ROW]`，无行级覆盖校验；表格文本与版面文本可能重复 | "漏了一半查不出来" |
| 检查类别留空 | 冲突检测全挤进 `(None, None)` 一组 | 冲突报告噪音大、跨组冲突检不出 |

## 3. 本次实测发现并修复的缺陷

### 3.1 同句式异字段规则被误合并（严重，已修）

`_text_similarity` 是**字符集合 Jaccard**（`rule_import_service.py:214`），对中文"同句式换一个字段"的区分度很低。实测：

```
报关单数量应不大于委托出口确认单数量  vs  报关单金额应不大于委托出口确认单金额   → 0.765  ≥ 0.75 合并
报关单数量应不大于委托单数量           vs  报关单重量应不大于委托单重量           → 0.833  ≥ 0.75 合并
发票金额应与报销单金额一致             vs  发票税额应与报销单税额一致             → 0.833  ≥ 0.75 合并
```

只要两条规则的 `scope + condition + exceptions` 相同（模板里通常就是"同一单据、无条件"），它们就会被**静默合并**，后者计入 `skipped` 并提示"已自动合并"。这正是设计文档里最强调的"数量、金额分别成条"的拆解结果，会被去重逻辑吃回去。

**修复**：`_assertion_subject`（`rule_import_service.py:242`）——当双方都有结构化断言且**断言主体（源/目标对象与字段）不同**时，直接判定为不同规则，不再走文本相似度；`operator` 不参与比较，避免同一约束的不同措辞被拆散。回归测试见 `tests/test_rule_import_granularity.py::DedupSemanticBoundaryTests`。

### 3.2 冲突检测：分组口径与"检测失败误清除"（已修）

**问题 A（安全）**：`detect_conflicts_in_rules` 在 LLM 调用失败时静默返回 `[]`，上层把它当成"没有冲突"，随即 `clear_old_conflicts` 清掉历史冲突，并对相关规则**自动 confirmed + enabled**。一次网络抖动就可能把因冲突被禁用的规则重新放行。

**问题 B（质量）**：分组键是 `(doc_type, check_category)`——两者都空的规则全挤进 `(None, None)` 一组（噪音大、费 token），而不同分组之间的真实冲突检不出来；送进提示词的只有 `rule_text` + 容差。

**修法**（`rule_conflict_detector.py`）：

1. **失败与无冲突分离**：新增 `detect_group()` 返回 `(冲突, 错误)`，`detect_all_conflicts()` 返回带完成度的 `DetectionResult`；`run_conflict_detection()` 只对**本轮完整检测过**的规则执行冲突回收，失败分组与超限截断的规则一律保持原状，并在响应中返回 `detection_incomplete` / `failed_groups` / `warnings`；导入链路把这些告警并入 `import_warnings`。
2. **按适用范围分组**：以 `scope.doc_types` 为准（缺省回退 `doc_type`），一条规则进入它涉及的每个对象分组；`ALL`/整批/未限定范围的规则单独成组；单成员分组视为已完整检测（用于回收历史冲突，且不调用 LLM）；单组超过 60 条按优先级截断并告警。
3. **提示词升级**：每条规则改为渲染「适用=… | 条件=… | 断言=… | 容差=… | 例外=…」，并明确列出**不构成冲突**的情形（范围不相交、条件互斥、断言主体不同、仅措辞不同）。
4. **跨分组去重**：同一对规则可能因多对象范围在多个分组被检出，按 (规则对, 类型) 去重。

回归测试：`tests/test_rule_conflict_detection.py`（11 项，含"LLM 失败不得清冲突/不得启用规则""单组失败不影响成功组""对手被删除后孤立规则的历史冲突可回收"）。

### 3.3 覆盖率统计发生在去重之前（已知，可接受）

`_compute_source_coverage` 用的 `covered_source_refs` 在去重前累加，被合并的行也算"已覆盖"。当前可接受（说明该行被解析过），但"一行多规则"无法校验，建议后续按 source_ref 统计规则条数分布。

## 4. 推荐的规则描述文档模板

### 4.1 设计原则：AI 多干活，人少干活

1. **必填只有 1 列（规则正文）**：其余列留空即交给系统从正文推断，且**留空不算信息缺失**、不会产生缺陷、不会让规则变成"待确认"。客户从"填 11 列"降到"填 1 列"。
2. **列按三档从左到右排列，档位直接写在表头**：`（必填）` / `（建议填）` / `（可留空）`，配单元格批注给示例；颜色区分（红/蓝/灰），不需要额外图例。
3. **一行 = 一条规则，一行只说一件事**：原子性判断、来源行校验、去重身份都以行为单位。
4. **只有正文说不清、或需要显式放宽时才补列**：多字段/多票据汇总补「比较关系」，需要放宽补「容差」，提示类规则补「复核策略」。
5. **表格用固定列名、单行表头、不用横向合并**：抽取器按首个非空行做表头，横向合并会触发"多级表头"推断。
6. **纵向合并可以用于"适用单据"这类重复值**：系统会把合并值继承到每一行，并记录 `merged_from` 供追溯。
7. **文档级场景与术语放在独立工作表/声明块**：整表可留空（留空按规则集默认场景）；场景中文名也可留空，系统自动取场景包名。

配套的提示词契约（否则"留空"会被模型当成信息缺失）：

- 通用契约包新增两条：列名档位标注只给人看，映射时按主名判断；**留空的列表示交由模型从正文推断，不是信息缺失**，不得据此报缺陷或降低 confidence；
- `missing_value` 缺陷口径收紧为"规则正文本身依赖一个未给出的阈值/期限"，不再因为金额/日期比对没写容差就报缺陷（容差缺失本来就由 `defaults.tolerance` 填 0，报缺陷只会让规则被禁用）。

### 4.2 模板结构（Excel，推荐）

| 工作表 | 作用 | 解析行为 |
|---|---|---|
| `填写说明` | 给编制人看的规范 | **跳过**，不参与解析（`_sheet_kind` → `skip`，`rule_document_import_service.py:124`） |
| `场景与术语` | 声明业务场景 + 术语别名（**整表可留空**） | 解析为**文档级声明**：场景键 → 选择场景知识包；术语 → 注入提示词并统一命名 |
| `规则清单` | 规则表本体，一行一条 | 逐行输出 `[SOURCE_ROW=规则清单!N]`，导入后可校验覆盖率 |

`规则清单` 的 9 列（按填写负担从低到高排列）：

| # | 列（表头自带档位） | 档位 | 映射到 | 说明 |
|---|---|---|---|---|
| 1 | 规则正文（判定内容） | **必填** | `rule_text` | 一句话：谁、和谁、比什么、什么方向；对象写全名 |
| 2 | 适用单据/对象 | 建议填 | `scope.doc_types`（单一对象同时填 `doc_type`） | 正文已写清全名时可留空，模型会推断；连续相同可纵向合并 |
| 3 | 触发条件/业务场景 | 建议填 | `structure.condition.text` + `rule_text` | 条件规则建议填（也是去重身份的一部分） |
| 4 | 例外 | 建议填 | `structure.exceptions` | 与主规则同行；写在正文里也可被提取 |
| 5 | 检查类别 | 可留空 | `check_category` / `intents` | 影响冲突检测分组；留空由模型按意图归类 |
| 6 | 复核策略 | 可留空 | 语义（硬性不符/人工确认/仅提示） | 降低"提示类规则被判失败"的误报 |
| 7 | 比较关系 | 可留空 | `structure.assertion` | 仅正文说不清或多票据汇总时填 |
| 8 | 容差 | 可留空 | `tolerance` | 仅在需要放宽时填；留空=严格 0 |
| 9 | 依据来源 | 可留空 | provenance | 制度/条款号，便于审查结果追溯 |

已删除的两列：**规则编号**（系统导入时自动生成 R0001…，冲突报告按系统编号引用）、**备注**（不进入规则，容易误导填写人写规划内容）。

### 4.3 场景与术语表怎么填（整表可留空）

```
项目        值            说明
场景        expense      可留空（按规则集默认场景）；可选 trade / expense / supplier / 自定义场景键
场景名称     （留空）      可留空，系统自动使用场景包中文名
适用说明     ...          可留空，仅作为解析上下文
术语        报销单        费用报销单、报销凭单      ← 规范名称 | 别名（多个用「、」）
```

文本类文档（Word/Markdown/TXT/PDF）用声明块实现同样能力：

```
场景与术语
场景：expense
术语：报销单 = 费用报销单、报销凭单
```

声明块会被**剥离**（`_parse_declaration_block`），不会变成规则，只用于选择场景包 + 注入术语。

## 5. Skill 的未来定位：三层结构，而不是"每个场景一个 Skill"

### 5.1 现状问题

- 原唯一内置 Skill（`backend/app/default_rule_parse_skill.yaml`，本次已拆分删除）把**通用解析契约**和**贸易单证领域知识**混在 25 条指令里；
- 它默认对**所有规则集**生效，非贸易场景只能整体关掉（`use_default_skill=False`），于是连通用契约也一起丢了；
- 客户要接入新领域，只能"再写一个 Skill"——把领域知识写成提示词文本、运维在数据库里，既不可评审也不可版本化。

### 5.2 目标结构

```
第 0 层  基础解析契约（代码）      prompt_templates.RULE_IMPORT_SYSTEM/USER
         输出 JSON schema、缺陷检测、来源行约束（表格行约束 _TABLE_ROW_SYSTEM_ADDITION）
第 1 层  通用契约包（数据，必装）  rule_parse_skills/00_通用解析契约.yaml   scenario = null
         场景无关：原子拆分、条件/例外归属、比较方向、模板列映射、术语优先、输出自查
第 2 层  场景知识包（数据，按需）  rule_parse_skills/10_贸易单证.yaml       scenario = trade
                                   rule_parse_skills/20_费用报销.yaml       scenario = expense
                                   rule_parse_skills/30_供应商审查.yaml      scenario = supplier（示例）
         领域术语 + 领域口径 + 类别同义词 + 领域优先级
第 3 层  规则集 Skill（数据库）    客户自己的纠偏覆盖（原有能力，不变）
```

合并顺序：内置（通用 → 场景）→ 规则集自定义；同键后者覆盖前者，列表追加、字典深合并（`rule_parse_engine.compile_directive` + `_merge_content`）。

### 5.3 场景键从哪来（优先级从高到低）

1. 导入接口显式参数 `scenario`（`POST /api/rules/import-batch` 的 body、`POST /api/graph/import-document` 的 query）；
2. **导入文件声明**（模板的「场景与术语」表 / 文本声明块）——推荐方式，规则文档自带上下文；
3. 规则集默认场景 `rule_sets.scenario`；
4. 兜底 `trade`（存量规则集都是贸易场景，保证升级不改变行为）。

未登记的场景键 → 只加载通用契约包（不会误注入其他领域知识），实现见 `default_rule_parse_skill.packs_for_scenario`。

#### 5.3.1 导入弹窗的两个下拉：出厂场景 / 自定义场景（互斥双通道）

两个下拉对应**两条互斥通道**，不再同时生效——勾了 Skill 就进入自定义场景，场景下拉随即禁用：

| 通道 | 触发 | 本次生效配置 |
|---|---|---|
| **出厂场景** | 业务场景下拉（不勾任何 Skill） | 通用解析契约（系统预设）+ 该场景的场景包 + 本规则集自定义 Skill |
| **自定义场景** | 勾选任意 Skill | 通用解析契约（系统预设）+ 勾选的 Skill；**不加载任何场景包** |

- 场景下拉只列**出厂场景包**（`pack.scenario != null` 的内置包，默认 `trade`）；
- Skill 下拉只列**自定义 Skill + 系统预设**，不再重复出厂场景包——这正是"两个下拉选项看起来重复"的根因；
  如果规则集还没有自定义 Skill，下拉里保留系统预设（通用规则解析契约），永远不会是空的；
- 未勾选任何 Skill 时，系统预设会引导 LLM 对未登记场景自主判断（见 §5.4 与"未定义字段"治理）。

装配语义实现：`rule_parse_engine.compile_directive_with_skills(preset_only=True)` 只装配通用契约包，
自定义通道再叠加勾选的 Skill（`rule_import_service.import_rules_with_skills`）。
导入结果回显 `scenario`（出厂场景键）与 `applied_skills`（实际生效的 Skill 清单），弹窗实时显示「本次生效装配」。

历史行为（已修正两次）：最早 `skill_ids` 非空会**整体替换**基线，导致只勾一个场景包就连通用解析契约一起丢掉；
上一版改成"场景包 + 勾选项"的无条件叠加，又会让客户的自定义场景被出厂领域知识污染。
现在按"两条互斥通道"落地：自定义场景通道既不加载场景包，也不自动带上未勾选的自定义 Skill。

### 5.3.2 检查项注册表与场景标签（未定义字段治理）

大模型在解析时会自主发明名字，过去系统对三样东西的管法并不一致：**文件类型**有注册表、审核、
管理页；**检查项**只是 `rule_sets.check_categories` 里一个字符串，写进去就长成规则列表的新列，
没人能改名或合并；**字段名**只有半套别名表。结果是"同一件事多个名字"在列表里繁殖，
而且图谱分派是按 `check_category` 字符串做的——名字写歪就从确定性校验悄悄降级成概率性审查。

本次治理（与「文档类型」对称）：

| 维度 | 落地方式 |
|---|---|
| 检查项注册表 | 新表 `check_intents`（name / aliases / sort_order / source / status），内置四类随租户 seed |
| 未知即登记 | 导入发现的新检查项登记为 `pending_review`，回传 `new_check_categories`，导入结果直接提示 |
| 人工确认 | 新增「检查项」页：确认 / 停用 / 改名（同步改写存量规则引用）/ 合并（旧名转别名）/ 删除 |
| 写时归一 | 导入时按别名表把名称映射到规范名；提示词**只喂已确认的检查项**，避免自造名称被自我强化 |
| 矩阵分列 | 规则列表只按**已确认**检查项分列，未确认的规则归入「未分类」并标注 `待确认：xxx` |
| 未登记字段 | 结构化断言引用未登记字段时，导入期挂 `info` 缺陷（不阻塞确认）并汇总为导入告警 |
| 场景标签 | `rules.scenario` 记录本次导入使用的场景知识包键，规则列表可按场景筛选与展示 |

配置项 `rules.auto_confirm_new_check_intents`（默认关闭）可让新检查项直接生效，跳过确认环节。

### 5.4 回答"能不能不用 Skill"

| 说法 | 结论 |
|---|---|
| "领域知识不该放在 Skill 里" | ✅ 正确。已下沉为场景知识包（YAML，可评审、可 diff、可复用） |
| "完全去掉 Skill 机制" | ❌ 不建议。Skill 是**唯一不需要改代码、不需要重启**就能修正解析行为的通道；客户纠偏、经验回写（`/skills/learn`）、灰度试错都依赖它 |
| "每个场景开发一个解析 Skill" | ❌ 不推荐（把数据写成代码：改一次口径就要动提示词文本、无法单测、无法复用）。场景包已覆盖这个需求 |
| "用模板替代 Skill" | ⚠️ 部分成立。模板把"客户能写清楚的东西"从提示词里拿走了，通用契约包因此可以从 25 条瘦身到 25 条（其中 3 条是新增的模板映射）；但"系统怎么理解结构化输出"必须留在契约里 |

**简化后的净效果**：贸易场景的合并提示词从"1 个包 25 条"变成"通用 25 条 + 场景 3 条"；新领域只需 1 个 YAML；客户 Skill 只写项目级差异。

### 5.5 向后兼容

- `RuleParseSkill.scenario` 新增列；启动时把存量内置记录（名称为"通用贸易规则解析配置"）升级为通用契约包，并为 `trade` 新建场景包；升级后贸易规则集的生效内容与升级前等价。
- `rule_sets.scenario` 新增列，默认 NULL → 兜底 `trade`；老客户零感知。
- `docs/通用贸易默认Skill.yaml` 仍是"trade 场景实际生效配置"的文档镜像，由 `scripts/sync_rule_parse_skills_docs.py` 生成，测试断言二者一致。

## 8. 后续建议（按性价比排序）

1. **Excel 导入预校验**：上传后先做列名/必填/重复检查（不调 LLM），把"规则编号重复""适用单据为空""比较关系写法不合法"在导入前返回，进一步降低无效解析。
2. **模板列直接映射（提速关键）**：对识别为标准模板的表格，按列直接映射契约字段、跳过 LLM，仅对"规则正文"这类自然语言列走 LLM 兜底；配合可配置的分段阈值（`_MAX_CHUNK_CHARS`）可把导入耗时降一个数量级。
3. **`validations` 真正执行**：当前 Skill 里的 `validations` 只编译不执行（`rule_parse_engine` 仅记录数量），建议在导入后处理阶段执行并回显。
4. **规则集 Skill 页签的场景分组**：内置知识包已有"通用 / 场景"标签，后续可按场景分组展示并支持一键停用某场景包。
5. **冲突检测再优化（按需）**：未限定范围的规则目前单独成组，与具体对象规则之间的冲突检不出；如客户大量使用"整批"规则，可对这类规则做"对象分组 × 整批"的定向配对（需控制 token）。
6. **真实文档 A/B 验收**：用客户原始规则表做"原文档 vs 模板文档"双路导入对比（人工修正条数、缺陷率、覆盖率、耗时），作为模板推广的依据。
