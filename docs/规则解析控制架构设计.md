# 规则解析控制架构设计

## 1. 问题诊断

### 当前流程（只有事后干预）

```
规则文档/文本
    ↓
[固定 System Prompt]  ← 无用户干预入口
    ↓
[LLM 解析]            ← temperature=0.1 只保证形式，不保证语义
    ↓
[JSON 规则]           ← confidence 是 LLM 自评，无外部校验
    ↓
[入库]                ← 去重逻辑简单，无冲突检测
    ↓
[用户确认/编辑]       ← 事后发现错误，逐条手工改
```

**三个断裂点：**
- **断裂 1**：用户无法在 LLM 解析前注入领域知识或修正指令
- **断裂 2**：LLM 没有能力主动识别规则文档中的信息缺失或语义冲突（prompt 里没要求）
- **断裂 3**：前端没有展示冲突/警告的机制，用户只能凭肉眼一条条翻

### 你的想法

> 用户编写 skills 事前控制大模型解析过程 → 即使原始文档不规范也能产出自定义的结果
> 语义缺失/冲突 → 精准识别 + 冲突报告 → UI 高亮 → 用户手工修正

## 2. 整体方案：三层控制架构

```
事前控制层 (Pre-control)
  ┌─────────────────────────────┐
  │  用户编写 Rule Parse Skill   │
  │  - 指令增强 / 字段映射       │
  │  - 默认值注入 / 文本预处理   │
  │  - 输出校验规则              │
  └─────────────┬───────────────┘
                ↓
事中解析层 (Parsing)
  ┌─────────────────────────────┐
  │  1. Skill 编译 → 动态 Prompt │
  │  2. LLM 解析（含缺陷检测指令）│
  │  3. 输出校验 + 冲突检测      │
  │  4. 产出：规则列表 + 冲突报告 │
  └─────────────┬───────────────┘
                ↓
事后确认层 (Confirmation)
  ┌─────────────────────────────┐
  │  UI 展示规则列表 + 冲突高亮  │
  │  冲突面板 + 逐条定位        │
  │  用户确认/修改/驳回         │
  └─────────────────────────────┘
```

## 3. 详细设计

### 3.1 规则解析 Skill 系统

#### Skill 层级结构

Skill 分两层，按优先级叠加：

```
层级               来源                   用户能否修改
─────────────────────────────────────────────────────
内置默认 Skill    系统自带（代码内置）       可以编辑（产生副本）
用户自定义 Skill  用户创建/导入             自由
```

**核心规则**：
- 每次规则解析时，**内置默认 Skill 始终生效**，保证开箱即用
- 用户可以**编辑默认 Skill**（保存时自动创建为副本作为该 RuleSet 的自定义 Skill，保留的原始默认不变）
- 用户可以**创建自己的 Skill**，覆盖默认 Skill 的对应能力
- 优先级：自定义 Skill > 内置默认 Skill。同名能力，自定义的覆盖默认的

#### Skill 存储

Skill 内容存数据库 `rule_parse_skills` 表，一个 RuleSet 关联一组 Skill。内置默认 Skill 的 `rule_set_id = NULL`（全局，不属任何规则集）。

```python
class RuleParseSkill(Base):
    __tablename__ = "rule_parse_skills"
    
    id: Mapped[uuid.UUID]
    rule_set_id: Mapped[uuid.UUID | None]    # NULL = 内置默认，非 NULL = 该规则集专用
    name: Mapped[str]
    is_builtin: Mapped[bool]                  # True = 内置默认，不可删除
    # 用户编辑内置默认时 → is_builtin=False, rule_set_id=当前规则集, parent_id=原默认
    parent_id: Mapped[uuid.UUID | None]       # 继承自哪个 Skill（版本追溯用）
    content: Mapped[dict]                     # YAML 解析后的 dict
    enabled: Mapped[bool]
    priority: Mapped[int]
```

#### Skill 作用域与覆盖机制

```
用户导入规则时：
  1. 加载内置默认 Skill → 生成 RuleParseDirective（基础指令）
  2. 加载该 RuleSet 的所有已启用自定义 Skill
  3. 逐能力合并：自定义 Skill 的同名 key 覆盖默认的
  4. 最终得到编译后的 RuleParseDirective → 执行解析

举例：
  内置默认的 defaults.tolerance.amount_percent = 5.0
  用户自定义 Skill 写了 defaults.tolerance.amount_percent = 3.0
  → 解析时 amount_percent 默认值 = 3.0（自定义覆盖默认）

  内置默认没有 field_mappings
  用户自定义 Skill 写了 field_mappings.doc_type = {"出口报关单": "报关单"}
  → 解析时生效 field_mappings（自定义新增）
```

#### Skill 如何影响 LLM 调用

编译层将 Skill 编译为 `RuleParseDirective` 对象：

```python
@dataclass
class RuleParseDirective:
    """从 Skill 集合编译得到的解析指令。"""
    prompt_additions: list[str]           # 注入到 System Prompt 的指令
    field_mappings: dict[str, dict]       # 输出字段映射
    defaults: dict[str, Any]              # 默认值
    validations: list[ValidationRule]      # 校验规则
    text_preprocessing: list[PreprocessStep]  # 文本预处理步骤
    term_normalization: dict[str, list[str]]  # 术语归一化映射
    domain_context: dict[str, Any]        # 领域上下文
```

新的 Prompt 结构变为：

```
System Prompt = 基础指令 + Skill 注入的 prompt_additions + domain_context
                                 ↓
User Prompt  = 文本预处理后的 raw_text + 可用枚举
                                 ↓
LLM 输出 → 应用 field_mappings → 注入 defaults → 运行 validations → 冲突检测
```

### 3.2 冲突/缺陷检测引擎

#### 检测维度

| 缺陷类型 | 检测时机 | 说明 |
|---------|---------|------|
| **MISSING_MANDATORY** | 输出校验 | 规则缺失必填字段（doc_type/check_category/rule_text 为空） |
| **ENUM_VIOLATION** | 输出校验 | doc_type/check_category 不在已注册枚举中 |
| **VALUE_OUT_OF_RANGE** | 输出校验 | tolerance 数值超出合理范围 |
| **FORMAT_VIOLATION** | 输出校验 | rule_text 不满足 skill 定义的格式规则 |
| **SEMANTIC_CONFLICT** | 规则间对比 | 两条规则的条件矛盾（如 A 要求 ≤5，B 要求 ≥10） |
| **LOGICAL_CONFLICT** | 规则间对比 | （报关单数量 ≤ 委托单数量） vs （报关单数量 ≥ 委托单数量） |
| **AMBIGUOUS_REFERENCE** | LLM 标注 | 规则中引用模糊的概念（如"相关日期"没指定哪个日期） |
| **INCOMPLETE_CONDITION** | LLM 标注 | 规则条件不完整（如"金额应一致"没说明和什么比） |
| **LOW_CONFIDENCE** | LLM 自评 | LLM 对这条规则的确信度低于阈值 |

#### 语义冲突检测逻辑

```python
def detect_semantic_conflicts(rules: list[dict]) -> list[Conflict]:
    """检测规则之间的语义冲突。"""
    conflicts = []
    
    # 1. 同 (doc_type, check_category) 组内的规则两两比对
    groups = group_by(rules, key=lambda r: (r.doc_type, r.check_category))
    for group_key, group_rules in groups.items():
        for i, a in enumerate(group_rules):
            for b in group_rules[i+1:]:
                conflict = compare_rules(a, b)
                if conflict:
                    conflicts.append(conflict)
    
    # 2. 跨组的隐性冲突（如同一字段在不同文件类型中的约束不一致）
    # 3. LLM 标注的模糊/不完整规则
    return conflicts


def compare_rules(a: dict, b: dict) -> Conflict | None:
    """两条规则是否冲突。"""
    # 提取语义约束对（通过 LLM 或规则解析）
    constraints_a = extract_constraints(a.rule_text)
    constraints_b = extract_constraints(b.rule_text)
    # 检测是否有矛盾
    return find_contradiction(constraints_a, constraints_b)
```

**关键设计**：语义冲突检测本身也可以调用 LLM（用小模型批量比对规则文本的语义矛盾关系），而非纯规则引擎。

#### LLM Prompt 增加缺陷检测指令

在 System Prompt 中增加：

```
### 缺陷检测指令
对每条被解析的规则，执行以下检查，结果放在 `defects` 数组中：

1. `ambiguous_reference`：规则中是否包含"相关""相应""有关"等模糊引用？
2. `incomplete_condition`：规则的条件是否完整？是否缺少比较对象？
3. `missing_value`：规则涉及金额/重量/时间但没有指定容差？
4. `contradiction`：这条规则是否和已解析的规则存在明显矛盾？
5. `uncertainty`：你对规则文本的理解有没有任何不确定的地方？

defects 数组的格式：
```json
{
  "defects": [
    {
      "type": "ambiguous_reference|incomplete_condition|missing_value|contradiction|uncertainty",
      "severity": "error|warning|info",
      "description": "问题描述",
      "rule_index": 该缺陷对应的规则在 rules 数组中的索引
    }
  ]
}
```
```

## 4. 实现路径（建议分阶段）

### Phase 1：缺陷检测 + 存储（地基）
- Rule 表加 defects 字段
- LLM Prompt 增加缺陷检测指令（不用 Skill 系统也能工作）
- 后端解析缺陷并入库
- 前端表格展示缺陷标签

**价值**：立刻就位，零改动成本，用户马上能看到哪些规则有问题。

### Phase 2：Skill 系统（核心能力）
- RuleParseSkill 模型 + 后端 CRUD
- 系统启动时自动 seeding 内置默认 Skill（`is_builtin=True, rule_set_id=NULL`）
- 每个新建 RuleSet 自动关联内置默认 Skill
- Skill 编译引擎（指令增强 + 字段映射 + 默认值注入 + 文本预处理 + 术语归一 + 领域上下文）
- 导入时 Skill 选择与合并
- 前端 Skill 管理页面：展示、编辑（编辑内置默认 → 自动创建副本）、新建、预览

### Phase 3：冲突检测 + UI 增强
- 规则间语义冲突检测
- 冲突报告展示
- 冲突概览横幅 + 跳转

## 5. 设计决策（已定）

| 决策项 | 结论 |
|--------|------|
| Skill 层级 | 内置默认 + 用户自定义。内置默认始终生效，自定义 Skill 按能力覆盖 |
| Skill 粒度 | 每个 RuleSet 独立绑定。不同客户的审查风格差异大，分开管理更灵活 |
| Skill 格式 | **YAML**（声明式、用户友好、有 Schema 模板可填空） |
| 编辑默认 Skill | 编辑保存时自动创建副本（is_builtin=False），指向该 RuleSet，不污染全局默认 |
| 新规则集的行为 | 新 RuleSet 自动继承系统内置默认 Skill，开箱即用 |
