# 项目基线：智能优先（LLM-First）

> **状态：基线（Baseline）。** 本文件是 DocGraph 所有需求、设计、实现、验收与代码评审的**前置约束**。
> 与其它设计文档冲突时，以本文件为准；确需违反的改动，必须在方案/提交说明里写明理由与退出计划。

---

## 0. 原则原文（项目所有者）

> 我更希望大模型更多参与判定，不要节省 Token，我讨厌规则引擎，因为不够灵活，不够通用性，不够泛化，
> 同时需要复杂的人工维护规则。这是我做这个项目要大量引入 LLM 的目的和基本原则，所有的需求修改和
> 架构调整建议，都不要违背这个原则，越来越多的规则补丁只会让后面的维护越来越困难，我们要找出通用解，
> 而不是场景定制的解。
>
> —— **更多智能，更少写死的规则，更少的人员维护，让 LLM 来帮助判断。**

## 1. 一句话判据

**任何改动，都要让"判断"更多发生在模型与数据里，而不是更多发生在代码分支里。**

## 2. 三条硬标准

| 标准 | 通过 | 不通过 |
| --- | --- | --- |
| **智能增量** | 让 LLM 的判断力更强、覆盖更广、更可复用 | 把 LLM 绕过去，用代码替它下结论 |
| **通用性** | 解决**一类**问题（换客户 / 换单据 / 换规则都不用改代码） | 解决**一个**场景（为某客户、某单据、某条规则加分支） |
| **维护成本** | 知识沉淀为数据，模型与数据自己长 | 需要人持续维护一份规则 / 别名 / 关键词清单 |

**Token 成本不是设计约束。** 不得以"省 Token、少调用"为理由减少 LLM 的参与度或降低判断质量；
性能问题的正解是**让 LLM 更快更多地参与**（并行批次、供应商侧提示词缓存、难例上强模型、失败反馈重试），
而不是"少用它"。

## 3. 反模式（禁止）

1. 为让某个场景通过，在 Python 里加"某字段 / 某单据类型 / 某客户 / 某条规则"的专用分支；
2. 靠关键词表、正则表、别名常量的膨胀来"修好"语义问题——它们只能作为**数据**存在，由 LLM 生成与维护；
3. 把 LLM 的结论再用规则引擎裁决一遍（**领域中立**的一致性 / 存在性 / 算术校验除外）；
4. 因为"模型不稳定"就把判定退回确定性引擎；
5. 为省 Token 裁剪证据、降低模型档位、跳过本该送审的条目。

## 4. 受鼓励的做法

1. **把人的知识变成数据**：字段绑定与别名自动沉淀升级、规则文档 → 解析 Skill、检查项自动生成；
2. **强化通用判定能力**：更完整的证据包、更通用的 check 原语、更好的提示词、更细的失败反馈与重试；
3. **让模型自我修正**：验证门打回时把"错在哪"回灌给模型重判，而不是由 Python 兜底改判；
4. **纯工程手段提升 LLM 吞吐**：批次并行、提示词缓存、模型分层（难例交更强模型）；
5. **把写死的领域规则迁成"数据 + 提示词"**。

## 5. 变更审查清单（每个需求 / 设计 / PR 逐条回答）

- **Q1** 这个改动里，"判断"发生在哪一层？（模型 / 数据 / 代码分支）——代码分支变多就要解释。
- **Q2** 新增的分支是通用的，还是绑定某个场景的？
- **Q3** 明天加第 462 条规则、换一个新客户、加一种新单据，还要改代码吗？要 → 不通用。
- **Q4** 这次的知识维护责任落在谁身上：模型 / 数据，还是人？
- **Q5** 我是在增强 LLM 的判断力，还是在替代它？
- **Q6** 有没有机会把这次的人工知识沉淀成数据，让下次不必再改代码？

结论写进方案或提交说明的一句话：

```
基线自审：通过
```
或
```
基线自审：违规 —— 理由：…；通用解为何暂不可行：…；退出计划：…
```

## 6. 现状对照（2026-11-20 取证）

**已经是基线资产（继续加厚）：**

- `review_intent` / `review_evidence` / `review_judge`：意图编译 → 证据包 → LLM 带引用判定 →
  **领域中立**的验证门（引用存在性、算术重算、结论自洽）→ 绑定沉淀；
- 判定失败把失败原因回灌重试，仍不过才显性交人工（模型优先，Python 只做通用校验）；
- 字段绑定命中阈值后自动升级为文档类型别名（人的知识 → 数据）；
- 规则解析 Skill 外置、规则描述模板、检查项（check intents）。

**历史包袱（触即迁，禁止再加）：**

- `graph_review_service.py`（1939 行、约 246 处中文业务字面量、20 处算子 / 单据类型分派）——
  判定逻辑的主要硬编码面；
- `doc_normalizer.py`（约 167 处）、`file_classifier.py` 的关键词与别名表；
- `seed_rules.py` 的内置规则定义。

迁移节奏：**不做一次性重写**。新需求一律走"证据 + LLM"路径；老分支只在被触及时顺手迁移（**触即迁**）。

## 7. 违反基线的真实案例（含一次自我撤回）

| 案例 | 判定 | 通用解 |
| --- | --- | --- |
| 为"容差 5% 导致验证门打回"，在 Python 里按规则容差放宽数值比较 | ❌ 把业务语义写进验证器 | 扩展**通用** check 原语（差值 / 比值 / 区间 / 存在性等），容差取值来自规则数据、由模型在 check 里声明，Python 只按通用算术语义重算 |
| 为"461 条规则 5 分钟"改成"结构化规则由引擎直判、LLM 只判残差" | ❌ 用代码替模型下结论（**本文件作者上一轮的建议，已撤回**） | 批次并行 + 提示词缓存 + 难例上强模型 + 证据聚焦，提高单位时间的智能量 |
| 把"规则结构编译成机器可判定谓词"当作根本解 | ❌ 规则引擎换个写法 | 让模型用通用原语表达可验证的比较，Python 只保留领域无关的校验能力 |
| 字段绑定命中阈值后自动升级为别名 | ✅ | 人的知识沉淀为数据，越用越少人工 |
| 验证门把失败原因回灌给模型重试 | ✅ | 让模型自我修正，而不是 Python 兜底 |

## 8. 与正确性的关系

智能优先 ≠ 放弃验证。任何结论仍必须能被证据验证；验证门必须保持**领域中立**：
只做存在性、算术、引用一致性、结论自洽这类通用校验，不引入业务容差、单据类型、客户口径。

## 9. 复审机制

- **每个需求 / 设计 / PR**：按 §5 自审，留一句话结论；
- **每个版本发布前**：按 §6 的方式重新取证一次，看硬编码字面量与分派分支的增减趋势；
- **发现违规**：先补通用路径，再考虑临时补丁；临时补丁必须写退出计划。
