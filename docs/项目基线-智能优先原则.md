# 项目基线：智能优先（LLM-First）

> **状态：基线（Baseline）。** 本文件是 DocGraph 所有需求、设计、实现、验收与代码评审的**前置约束**。
> 与其它设计文档冲突时，以本文件为准；确需违反的改动，必须在方案/提交说明里写明理由与退出计划。
>
> 变更记录：2026-11-20 建立；**同日修订**——澄清"不放弃规则引擎，放弃的是人工对规则的维护与设置"。

---

## 0. 原则原文（项目所有者）

> 我更希望大模型更多参与判定，不要节省 Token，我讨厌规则引擎，因为不够灵活，不够通用性，不够泛化，
> 同时需要复杂的人工维护规则。这是我做这个项目要大量引入 LLM 的目的和基本原则，所有的需求修改和
> 架构调整建议，都不要违背这个原则，越来越多的规则补丁只会让后面的维护越来越困难，我们要找出通用解，
> 而不是场景定制的解。
>
> —— **更多智能，更少写死的规则，更少的人员维护，让 LLM 来帮助判断。**

**2026-11-20 修订（消除歧义，优先级高于上文）**：

> 本项目里可以有很多的确定性规则，来保证执行的速度和准确性；但是这些规则都是 LLM 导入、解析、
> 智能判断、维护的，只有 LLM 无法判定的情况，才引入人工审查。就完全符合我的设计：自然语言文本导入
> → LLM 拆分为规则 → 检查规则冲突和警告 → 人工修正 LLM 无法自判断的规则。
> 虽然规则引擎还在，但是规则的导入和维护人不用参与，或者少参与。**不是完全放弃规则引擎，
> 而是放弃大量人工对规则引擎的维护和设置。**

## 1. 一句话判据

**任何改动，都要减少"人"在规则生命周期（导入 → 拆分 → 冲突检查 → 执行 → 维护 → 修正）里的参与。
确定性规则可以很多，但它们必须是 LLM 产出与维护的数据，而不是人手写的代码分支。**

## 2. 四条硬标准

| 标准 | 通过 | 不通过 |
| --- | --- | --- |
| **人的参与度** | 规则由 LLM 导入、拆分、冲突检查、维护；人工只在 **LLM 判不了**时介入 | 需要人手工写规则、改别名、加关键词、调判定分支 |
| **速度与准确性** | 用确定性规则（**LLM 生成的数据**）保证执行速度与结论一致性 | 为了"智能"把速度/准确性牺牲到不可用；或为了快而砍掉 LLM 的判断 |
| **通用性** | 换客户 / 换单据 / 换规则集，导一份自然语言文档即可，不改代码 | 为某客户、某单据、某条规则加人手写分支 |
| **闭环沉淀** | 人工修正一次 → 变成规则或知识数据，下次自动生效 | 同类问题反复人工修正（人变成了系统的一部分） |

**Token 成本不是设计约束**：不得以"省 Token、少调用"为理由减少 LLM 在**规则理解、冲突检查、语义判定**
上的参与。注意这与"用确定性规则保证速度"不冲突——确定性规则本身就是速度手段，只要它由 LLM 维护。

## 3. 反模式（禁止）

1. **人手写、人工维护**规则、别名表、关键词表、判定分支；
2. 人工修正之后**不沉淀**——同一类修正出现第二次；
3. 需要"人读文档 → 人拆规则 → 人改代码/配置"的流程；
4. 为了让某个场景通过，加人手写的专用分支；
5. 为省 Token 砍掉 LLM 在规则理解、冲突检查、语义判定上的参与；
6. 把"规则引擎"整体当敌人：**规则引擎可以有、而且应当多；违规的是人维护，不是规则存在**。

## 4. 受鼓励的做法

1. **规则生命周期全交给 LLM**：自然语言/文档导入 → 拆分 → 冲突与风险警告 → 结构化落库 → 版本演进；
2. **确定性规则规模化**：把 LLM 产出的谓词、比对、齐套、时限、容差规则交给引擎高速执行，保证一致性与速度；
3. **LLM 判定规则覆盖不到的语义情形**：字段名等价、角色签字、例外条款、模糊表述、跨单证语义；
4. **人工只处理 LLM 判不了的**，且修正结果回灌为规则 / 别名 / 绑定 / 提示词，形成闭环；
5. **纯工程提速**：批次并行、提示词缓存、模型分层、失败原因回灌重试。

## 5. 变更审查清单（每个需求 / 设计 / PR 逐条回答）

- **Q1** 这次新增或修改的规则 / 分支，是 **LLM 产出与维护**的，还是人手写的？
- **Q2** 明天加第 462 条规则、换新客户、加新单据，需要人改代码或配置吗？需要 → 不通用。
- **Q3** 这次改动里，人工介入点是不是"LLM 判不了"？人工的结论有没有沉淀成数据或规则？
- **Q4** 这次改动让系统更快 / 更准了吗？靠的是确定性规则（LLM 产出的数据），还是靠砍掉智能？
- **Q5** 有没有机会把这次的人工知识沉淀成数据，让下次不必再人工？
- **Q6** 判断链路上 LLM 的职责是变大还是变小？变小必须给出明确理由（例如纯算术、存在性这类无需智能的环节）。

结论写进方案或提交说明的一句话：

```
基线自审：通过
```
或
```
基线自审：违规 —— 理由：…；通用解为何暂不可行：…；退出计划：…
```

## 6. 现状对照（2026-11-20 取证）

**已经是基线资产（继续加厚）：**

- 规则文档导入 + 规则解析 Skill 外置 + 规则描述模板：自然语言 → 结构化规则；
- 规则冲突检测与警告（`rule_conflict_detector`）；
- 检查项（check intents）、字段绑定与别名自动沉淀升级（人的知识 → 数据）；
- `review_intent` / `review_evidence` / `review_judge`：意图编译 → 证据包 → LLM 带引用判定 →
  领域中立的验证门（引用存在性、算术重算、结论自洽）→ 失败原因回灌重试 → 绑定沉淀。

**历史包袱（触即迁，禁止再加）：**

- `graph_review_service.py`（1939 行、约 246 处中文业务字面量、20 处算子 / 单据类型分派）；
- `doc_normalizer.py`（约 167 处）、`file_classifier.py` 的关键词与别名表；
- `seed_rules.py` 的内置规则定义。

**重要澄清**：这些之所以是包袱，**不在于它们是规则引擎，而在于这些规则是人手写死在代码里的、
没有 LLM 维护通道**。迁移目标不是删掉规则引擎，而是：**把规则从代码搬进数据，并建立 LLM 的
产出与维护通道**（导入 → 拆分 → 冲突检查 → 人工只修 LLM 判不了的 → 落库 → 版本演进）。

迁移节奏：**不做一次性重写**。新需求一律走"LLM 产出规则 / 证据 + LLM 判定"路径；老分支只在被触及时
顺手迁移（**触即迁**）。

## 7. 判定实例（含一次自我纠偏）

| 案例 | 判定 | 说明 |
| --- | --- | --- |
| 人手写一条客户专用判定分支 | ❌ | 人维护，场景定制 |
| 人工维护别名表 / 关键词表 | ❌ | 除非该表本身由 LLM 生成与维护 |
| 把 LLM 解析出的规则编译成可执行谓词，交引擎高速执行 | ✅ | 规则是 **LLM 产出的数据**；这正是"确定性规则很多"的正解 |
| 容差由规则数据声明，引擎按数据执行 | ✅ | 值来自 LLM 解析，不是人写死在代码里 |
| 结构化规则交确定性引擎直判，LLM 判语义/例外与规则演进 | ✅ | 前提：规则由 LLM 产出与维护（**本节曾把此条误判为严重违规，已纠偏**） |
| 人工兜底判定且不沉淀 | ❌ | 人变成系统的一部分 |
| 为省 Token 少送审一部分规则 | ❌ | 砍智能 |
| 字段绑定命中后自动升级为别名、验证门失败原因回灌重试 | ✅ | 闭环 |

## 8. 与正确性的关系

智能优先 ≠ 放弃验证。任何结论仍必须能被证据验证；验证门保持**领域中立**（存在性、算术、引用一致性、
结论自洽），业务语义（容差、单据类型口径）作为**数据**由规则声明、由引擎执行。

## 9. 复审机制

- **每个需求 / 设计 / PR**：按 §5 自审，留一句话结论；
- **每个版本发布前**：取证三项趋势——
  1. 人手写的规则 / 分支 / 关键词字面量：**应下降**；
  2. LLM 产出并落库的规则占比、绑定与别名自动沉淀量：**应上升**；
  3. 人工介入率（人工修正规则次数、`escalated` 交人工率）：**应下降**；
- **发现违规**：先补通用路径（LLM 产出 + 数据化 + 沉淀闭环），再考虑临时补丁；临时补丁必须写退出计划。
