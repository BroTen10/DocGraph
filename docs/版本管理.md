# DocGraph 版本号管理

一句话：**版本号只写在一个地方**——仓库根 `VERSION` 文件；「这次跑的是哪个提交」由 git 或构建注入补齐；
本机开发、服务器镜像三处都用同一口径（`backend/app/version.py`）报版本，所以可以直接对比。

## 单一真相

- `VERSION`：一行 semver，例如 `0.3.0`。**改版本号只改这一个文件**，不要在别处再写第二份。
- 发版 tag：`v` + VERSION，例如 `git tag v0.3.0`。tag 是"这个版本号对应哪个提交"的锚点。
- 提交定位不写进文件，由 git 提供：`git describe --tags --dirty --always`（本机开发环境因此能精确到提交）。

## 版本信息结构（`GET /api/version`）

本机与服务器返回同一结构，逐项对齐即可看出差异；`GET /api/health` 也带 `version / label / commit / dirty / build_env` 这五个常用字段。

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `kind` | 来源端 | `backend`、`frontend` |
| `name` | 项目名 | `DocGraph` |
| `version` | 人类版本号（`VERSION` 文件或构建注入） | `0.3.0` |
| `label` | 一行标识 = `version+commit[.dirty]` | `0.3.0+4b00ac1.dirty` |
| `describe` | `git describe` 原文 | `v0.2.0-36-g4b00ac1` |
| `tag` | 最近一次发版 tag | `v0.2.0` |
| `commit` / `commit_full` | 短 / 完整提交号 | `4b00ac1` |
| `commit_date` | 提交时间（ISO 8601） | `2026-10-14T08:59:16+08:00` |
| `branch` | 分支 | `master` |
| `dirty` | 工作区是否有未提交改动；`null` = 判断不了（git 不可用） | `true` |
| `build_env` | `dev` = 从 git 工作区运行；`prod` = deploy.sh 构建的镜像；`unknown` = 两者都不是 | `dev` |
| `built_at` | 构建时间，由部署脚本注入 | `2026-10-14T01:16:24Z` |
| `source` | 版本信息的来源 | `runtime-git` / `build-args` / `version-file` / `unknown` |

## 三种环境的取值来源

| 环境 | 怎么取版本 | `source` |
| --- | --- | --- |
| 本机后端（`start_services.bat` → uvicorn） | 运行时读工作区 `.git`；git 不在 PATH 时**直接读 `.git/HEAD`**，提交号与分支仍能拿到 | `runtime-git` |
| 本机前端（`vite dev` / `npm run build`） | 构建期读 `VERSION` 文件 + 本机 git，注入 `__BUILD_INFO__` | `runtime-git` |
| 服务器镜像（`bash deploy.sh`） | `deploy.sh` 在宿主机算好，经 compose `build.args` → 镜像 ENV（容器里没有 `.git`） | `build-args` |
| 未经 deploy.sh 直接 `docker compose --profile deploy build` | 只能读到镜像内没有的 `VERSION`，如实报 `0.0.0` / `unknown` | `version-file` / `unknown` |

> 说明：Windows 上「装了 Git 但没把 git 加进 PATH」很常见，所以后端**不强依赖 git 可执行文件**：
> 提交号与分支直接解析 `.git/HEAD`（含 `packed-refs`、worktree 的 gitdir 指针）。
> 只有 `describe` / `tag` / `dirty` / 提交时间这几项需要 git 命令，缺失时返回 `null`（前端显示「未知」，不假装干净）。

## 怎么对比本机与服务器

1. **本机后端**：浏览器或 `curl http://localhost:8800/api/version`。
2. **服务器**：`curl https://<域名>/api/version`；每次 `bash deploy.sh` 结束时脚本也会打印「运行版本」。
3. **一条命令对比两边**：

   ```powershell
   powershell -File scripts\version.ps1 -Remote https://<域名>
   ```

   脚本同时给出「本机工作区（代码）」「本机运行中后端」「服务器正式环境」三行，并按提交号给结论。
4. **界面**：右上角版本徽标（悬停看前后端明细）；「系统设置 → 版本信息」有完整表格。
5. **判定口径**：先比 `version`，再比 `commit`；`dirty=true` 表示该环境的代码有未提交改动——这正是"环境差异"的常见来源。

## 发版流程

```bash
# 1) 改版本号（唯一一处）
vi VERSION                     # 例如从 0.2.0 改成 0.3.0
git add VERSION
git commit -m "chore: 版本号升到 0.3.0"

# 2) 打 tag 并推送（tag 名 = v + VERSION）
git tag v0.3.0
git push && git push --tags

# 3) 服务器升级
cd /opt/docgraph/app && git pull && bash deploy.sh
```

- `deploy.sh` 会在 `VERSION` 与现有 tag 对不上时**告警但不阻断**（开发中途部署很常见）。
- 工作树有未提交改动时也会告警：镜像会带 `dirty` 标记，正式发布请先提交。

## 常见问题

| 症状 | 原因与处理 |
| --- | --- |
| 徽标显示「版本未知」 | 镜像不是用 `deploy.sh` 构建的（build args 为空）。用 `bash deploy.sh` 重新构建。 |
| 徽标橙色「版本不一致」 | 前端资源与后端接口不是同一次构建：先 `Ctrl+F5` 强刷；仍不一致就 `bash deploy.sh` 重建两个镜像。 |
| 提交号显示 `—` | 该环境拿不到 git：容器内属正常（应由构建注入）；本机可把 git 加入 PATH，之后 `dirty` / `describe` 也会一起出现。 |
| `dirty` 显示「未知」 | git 命令不可用，无法判断未提交改动；本机把 git 加入 PATH 后即可显示。 |
| 徽标灰色「只能比对版本号」 | 至少一侧没有提交定位，只能确认版本号一致，不能确认提交一致。 |
| 服务器版本比本机旧 | 到服务器 `git pull && bash deploy.sh`，再用 `scripts\version.ps1 -Remote` 复核。 |
