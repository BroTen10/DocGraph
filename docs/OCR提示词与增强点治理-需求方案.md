## 一、需求背景与核心问题

### 1.1 触发案例

增值税发票票面有「备注」栏，备注中常含审查需要的信息（合同号、项目名称、业务说明等）。当前 DocGraph 的增值税发票字段模板是：

```
DOC_VAT_INVOICE key_fields = [合同号, 发票号码, 购货方, 销货方, 金额, 税额, 价税合计, 开票日期]
```

清单里**没有「备注」**。链路因此是：字段清单不含备注 → 提示词不要求模型读备注 → 多模态模型"合理地"忽略备注栏 → 备注信息既不进入 `extracted_fields`，也不产生任何告警。用户描述为「默认 OCR 识别忽略了备注信息」。

这不是单个字段的疏漏，而是一类系统性缺口：**抽取范围只由「文档类型 → 字段清单」一处决定，清单之外的信息丢失且不可见**。

### 1.2 核心用户问题

需求不是"加一个设置页"，要解决的是四个问题：

- **Q1 静默漏抽**：字段清单之外的信息（备注、附加条款、明细附加列）系统性丢失，丢失不可见、不可测、不告警。
- **Q2 修正不沉淀**：现状唯一纠偏手段是人工改字段值或改全局提示词；修正结果不回流，同类错误下一张单必然复现。
- **Q3 提示词无版本、无作用域**：OCR 提示词是全局单例（`ocr.image.*` / `ocr.text.*`），不能按单据类型 / 版式 / 客户分化；改动无历史、无回退，出错时无法复现"当时用的是哪版"。
- **Q4 无回归验证**：没有金标准样本集和字段级准确率，改提示词只能靠"感觉变好了"，无法证明没有把别的单据改坏。

### 1.3 目标用户

- **主要**：交付 / 实施工程师（FDE）——在现场为新客户、新版式快速补齐抽取能力。
- **次要**：业务复核人员（在 OCR 对照页纠错、确认沉淀）；平台管理员（管理增强点的生效范围与版本）。

### 1.4 一句话价值

把「每次手工纠错」变成「可复用的单据级抽取资产」：让 OCR 越用越准，且每次识别都可解释（用了哪版增强点）、可复现、可回退。

## 三、行业调研：OCR 增强点如何被"积累与固化"

按增强点落在哪一层，归为 5 类；每条都取自实际抓取的厂商 / 开源文档。

### 3.1 模板与字段层：把版面知识固化成模板和字段词典

- **百度智能云 iOCR 通用版**：`自定义模板`——上传一张模板图片即可建立图中文字的 Key-Value 对应，无需训练；`自定义字段类型`——对取值有限的字段上传**字段词典**限制输出范围，系统做"输出值的智能纠正匹配"；另有 `自定义分类器`（每类 30 张训练图）实现版式自动分类。
  出处：<https://cloud.baidu.com/product/ocr/iocr>
- **阿里云 文档智能 · 单据票证信息抽取**：支持**用户自定义抽取字段**，平台可视化标注 + 模型训练；同时提供**字段类型管理**（通用字段 / 自定义字段）与**题目库**——同一模型复用同一题库，以"确保其字段设置完全相同"。
  出处：<https://help.aliyun.com/zh/document-mind/product-overview/bill-and-ticket-information-extraction>

→ 可借鉴：**"要抽什么"是一份可维护的字段资产**；枚举值用**词典纠错**兜底；同一业务对象复用同一份字段定义，杜绝各处分叉。

### 3.2 样本与模型层：少量标注 → 自学习 / 微调

- **阿里云**：≥20 张同类样本即可建模型，"通过 100+ 训练样本标注，调优后模型识别准确率可超 95%+"；流程固化为 数据准备 → 标注（含智能预标注加速）→ 训练 → 评测。出处同上。
- **Azure Document Intelligence `custom neural model`**：深度学习模型，结合 layout + language 特征抽取**已标注字段**；与 template model 共用同一套标注格式；v4.0 支持签章检测、表格单元格置信度、重叠字段。
  出处：<https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-neural>
- **AWS Textract `AnalyzeExpense`**：发票 / 收据专用结构化 API（同步 `AnalyzeExpense`、异步 `StartExpenseAnalysis`）——把"某类单据抽哪些字段"做成产品级专用入口，而非让调用方自行拼提示词。
  出处：<https://docs.aws.amazon.com/textract/latest/dg/analyzing-document-expense.html>

→ 可借鉴：**标注样本是最重、也最"固化"的资产**；样本要覆盖版式差异而非只挑干净的；置信度要下沉到字段 / 单元格粒度。

### 3.3 后处理规则层：正则 / 词典 / 锚点 + 逻辑一致性校验

- **百度智能云《OCR 后处理：从识别到精准文本的进阶之路》**：基于规则的纠错（预设字典、正则）、格式标准化（结构化字段提取）、**逻辑一致性校验**（如"收入 100 万、利润 200 万"这类字段间矛盾检测）、**领域专属字典**应对专业术语稀疏，并明确"**通过用户反馈积累错误案例，定期更新纠错字典与模型**"；关键字段（金额 / 日期）要求近 100% 准确，评测用准确率 / 召回率 / F1。
  出处：<https://cloud.baidu.com/article/3805884>

→ 可借鉴：提示词之外，**确定性的后处理规则同样是增强点**，更便宜、更可解释；**错误案例正是纠错字典的原料**。

### 3.4 提示词层：自然语言查询 + 版本化 + 指标驱动优化

- **AWS Textract `Queries`**：用自然语言 question 向文档提问（示例 "What is the patient first name?"），返回答案 + 置信度 + 页面位置，无答案则留空。说明"按问题抽取字段"在成熟 OCR 产品里已是一等能力。
  出处：<https://docs.aws.amazon.com/textract/latest/dg/queryresponse.html>
- **Langfuse Prompt Management**：同名 prompt 的更新自动成为**新版本**，用 `labels`（如 `production`）做发布与晋升，模板支持变量占位符。
  出处：<https://langfuse.com/docs/prompts/get-started>
- **DSPy**（arXiv 2310.03714）：把 pipeline 抽象为模块图，用 compiler 按**给定指标**自动优化提示词与示例，替代手写模板的 trial-and-error。
  出处：<https://arxiv.org/abs/2310.03714>

→ 可借鉴：**提示词必须有版本与发布标签**；**"提问式抽取"**比"整页字段清单"更适合长尾信息（备注这类"有则抽、无则空"的字段）；提示词优化应由评测集驱动，而不是即兴手改。

### 3.5 闭环治理层：修正回流 → 评测集 → 指标 → 门禁

- 阿里云把"标注 → 训练 → 评测"固化为平台内的任务流程；百度后处理文明确"用户反馈积累错误案例 → 定期更新字典与模型"，并给出字段级指标口径；腾讯云文档智能把抽取能力分档——基础版覆盖 6000+ 种固定版面证照单据（网约车行程单、驾驶证、运输证、房产证等），多模态版支持不限定版式（报关单、装箱单、运单、提单等），即"已固化的常见版式"与"长尾版式"分层承接。
  出处：<https://cloud.tencent.com/product/smart-ocr>（及 3.1、3.3 两条）

→ 可借鉴：增强点必须闭环——**发现（漏抽 / 误抽）→ 沉淀（字段 / 规则 / 词典 / 指令）→ 验证（金标准样本）→ 生效（版本发布）→ 可回退**。

### 3.6 归纳：5 条可借鉴规律

- **B1** 抽取范围是可维护资产（字段清单 + 词典 + 模板），不写死在提示词里。
- **B2** 增强点必须能按"单据类型 / 版式"分化，而不是全局一版。
- **B3** 长尾信息用"有则抽、无则空 + 低置信度兜底"，并在结果里可见。
- **B4** 一切改动要版本化 + 可回退，并记录"这次识别用了哪版"。
- **B5** 用金标准样本集 + 字段级指标做回归门禁；人工修正要能一键沉淀为候选增强点。

## 五、机制实测（2026-10-13，真实单据）

**要回答的问题（D2 追问）**：在文档类型的字段清单里加一个字段名，当前状态下能不能引导 OCR 抽出备注等非主表区域的信息？

**方法**：不改任何代码，走仓库自身代码路径（`app.ocr_client.recognize` + `prompt_templates` 内置提示词），对同一张真实单据图片（`backend/uploads/24HCSP012260253/付款申请 CNPAY202407180044.png`，票面含「付款用途 / 附言 / 付款用途备注 / 交易附言备注」等备注类栏目）跑三组字段清单，每组重复 2 次（`temperature=0.1`）。探针脚本跑完即删，未写数据库。

| 组 | 字段清单 | 第 1 次 | 第 2 次 |
|---|---|---|---|
| A 基线 | 付款申请内置模板：合同号 / 申请金额 / 申请日期 / 申请人 | 合同号=`24HCSP012260253-10`；申请人=`智显业务部-江航` | 合同号=`24HCSP012260253-10；24HCSP012260240-10`（两个值）；申请人=`智显业务部-江航` |
| B 加字段 | A + 付款用途 / 附言 / 采购合同号 | **合同号=`null`**（进低置信）；采购合同号=`24HCSP012260253-10;24HCSP012260240-10`；付款用途=`货款`；附言=`付货款` | 同上（合同号仍为 `null`） |
| C 加非字面标签 | A + 支付附言（票面无此标签） | 支付附言=`付货款`；**申请人=`智显业务部`**（被截断） | 同上 |

**结论**

1. **加字段确实能引导抽取，方向成立。** B 组新加的「付款用途」「附言」抽到了正确值；C 组的「支付附言」在票面上没有同名标签，模型仍稳定映射到「附言」栏的 `付货款`。即"字段清单 → 提示词 → 模型去找"这条链路是通的，且允许一定语义映射。
2. **但当前实现下会带来回归。** B 组把原有「合同号」挤成 `null` 且两次复现；C 组把「申请人」的取值粒度改掉（`智显业务部-江航` → `智显业务部`）。"只加不改"的假设不成立：改字段清单可能悄悄改坏已有字段。
3. **同一张图两次结果不一致，且没有回归集就发现不了。** A 组合同号一次给出 1 个值、一次 2 个值；`low_confidence_fields` 是模型自报的弱信号——A 组明明抽到值仍被标低置信，B 组 `null` 也被标低置信，无法区分"没抽到"与"票面本来没有"。

→ 因此一期的"类型级提取指令 + 补充字段"必须配套：字段命名与归属的显式约定、变更后的抽样对比（同批样例改动前后各跑一次）、生效快照。这三条也是三期"评测集 + 门禁"的需求依据。

## 六、需求方案（分四期）

> 一期为 MVP，必须先做；二~四期按 ROI 与客户压力排期。

### 一期（MVP）：单据级 OCR 增强点 + 备注类字段抽取 + 生效快照

**用户故事**

- 作为 FDE，我希望为某个单据类型（如增值税发票）维护一段**本类型专属的抽取指令**，让模型按本类型特点读取备注等信息。
- 作为 FDE，我希望**重新 OCR 时能看到并选择**本次使用的增强点，以便针对性重跑、不影响其他单据。
- 作为复核人，我希望漏抽的字段表现为**可见的空值 + 低置信度提示**，而不是静默消失。

**功能点**

- **FR-1** 文档类型新增「OCR 增强点」：`ocr_extract_instructions`（该类型专属抽取指令，如"备注栏也要逐字扫描"）+ `ocr_extra_fields`（备注内**关键字段**清单，逐个结构化，如 `备注-合同号` / `备注-项目名称` / `备注-共计金额`；**不做整段「备注」字段**）。作用域按 D2 定为**全局**，字段清单来源=**文档类型已定义字段**。
- **FR-2** 提示词组装按 `doc_type` 注入增强点（模板新增扩展占位符）；**未配置时行为与现状逐字段一致**（向后兼容）。
- **FR-3** 备注类字段"有则抽、无则空"：命中返回原文文本；未命中返回 `null` 并进 `low_confidence_fields`；备注类字段**不做金额 / 日期归一**，避免误伤。按 D4，备注类关键字段**要参与规则审查**：只要落进 `documents.extracted_fields`，规则以「文档类型 + 字段名」引用即可生效（`graph_review_service._field_value` / `review_service` 均直接读 `extracted_fields`，审查引擎无需改造）。
- **FR-4** 重新 OCR（单文档 / 合同级）可选范围：`类型增强点（默认）` / `仅基础字段模板`。
- **FR-5** 每次 OCR 任务写**生效快照** `ocr_tasks.applied_config`（增强点版本号 + 提示词 key / 版本），供追溯与复现。

**数据与接口（建议）**

- `document_types` 加列：`ocr_extract_instructions`(Text)、`ocr_extra_fields`(JSONB)；`DocumentType` CRUD 相应扩展。
- 新增 `GET /api/doc-types/{id}/ocr-profile` 返回该类型当前生效增强点。
- `ocr_tasks` 加列 `applied_config`(JSONB)。

**前端落点**

- 「文档类型」页：新增「OCR 增强点」编辑区（指令 + 补充字段）。
- OCR 对照页：备注类字段以"补充字段"分组展示，空值 / 低置信度可辨；重跑按钮旁提供范围选择。

**非目标**：不做样本微调、不做多人协同标注、不做自动优化提示词。

#### 字段命名规范（D1 落地口径，已定）

- **形式**：`备注-<语义名>`，前缀固定 `备注-`，语义名用业务上能直接读懂的短名。例：`备注-合同号`、`备注-项目名称`、`备注-共计金额`、`备注-建筑服务发生地`。
- **为什么不做整段「备注」**：长自由文本的结构化不稳定，且审查规则无法引用一段散文；拆成原子字段后既能进规则，又能逐字段判对错。
- **与现有归一化链路的相互作用**（代码事实，直接决定"该起什么名字"）：`normalize_fields` 按**字段名关键词**决定归一行为——
  - 含「金额 / 总价 / 价税合计 / 税额」→ 金额归一为纯数字，所以 `备注-共计金额` 可直接参与金额比对；
  - 含「日期 / 时间」→ 归一为 `YYYY-MM-DD`；
  - 含「数量 / 件数」→ 数字；含「重」→ 数字；
  - 以「币种 / 币别 / 币制」结尾 → 币别归一，故要表达币种时用 `备注-币别`；
  - 其余（如 `备注-项目名称`、`备注-建筑服务发生地`）原样保留为文本。
- **必须规避的坑**：`normalize_fields` 与 `cross_validate_contract_no` 都按"键名含『合同』且含『号』"识别合同号字段，而 `review_service` / `ocr_task_service` 随后会调 `cross_validate_contract_no(doc.file_name, …)`，用**文件名**里的合同号做 ground truth 覆盖。即 `备注-合同号` 会被文件名覆盖：当备注里的号**就是**合同号时这是想要的（防末位误识）；当备注里可能是**另一个号**（订单号、分批号）时会改错。→ 处理方式见 D6。
- **规则引用方式**：规则的 `assertion.source/target.field` 直接写 `备注-合同号`（`doc_type=增值税发票`）；需要别名时走文档类型的 `field_aliases` 登记。

### 二期：可配置后处理规则 + 字段词典

- **FR-6** 类型级后处理规则（锚点关键词 + 正则 + 目标字段），把当前写死在 `field_extraction_service` 的规则外置为可维护资产（内置规则作为默认值保留）。变更时应支持"同批样例改动前后各跑一次"的抽样对比（见第五章实测得出的回归风险）。
- **FR-7** 字段词典（枚举取值白名单 + 智能纠正匹配，借鉴百度 iOCR「自定义字段类型」）：近似值自动纠正并留痕。

**非目标**：暂不支持用户自定义脚本，仅正则 + 词典，规避安全与可解释性风险。

### 三期：修正回流 + 金标准评测集 + 字段级指标

- **FR-8** OCR 对照页「一键沉淀」：对人工修正生成候选增强点（补充字段 / 后处理规则 / 指令片段）→ **人工确认后**入库，绝不自动生效。
- **FR-9** 回归评测集：维护金标准样本（类型 + 期望字段），支持"改增强点前后跑评测"，输出字段级准确率 / 召回率与差异。
- **FR-10** 生效门禁：增强点变更前可选择要求评测通过（阈值待定）。

**非目标**：不做模型训练（保留为四期可选）。

### 四期：作用域分化 + 版本对比回退 +（可选）样本微调

- **FR-11** （按 D2 降级为可选）增强点作用域三级覆盖：全局 / 规则集（客户）/ 单据类型，优先级明确。
- **FR-12** 版本历史与回退：历史版本列表、diff、一键回退；识别结果可回链到当时版本。
- **FR-13（可选）** 用累积样本对接私有化 / 云端微调（在"数据不出域"约束下默认关闭）。

## 七、边界条件

| 维度 | 边界场景 | 处理方式 | 写入方案 |
|---|---|---|---|
| 内容 | 备注为空 | 字段返回 `null` + 进 `low_confidence_fields` | 是 |
| 内容 | 备注超长（超 token 预算） | 截断 + 标记 `truncated`，提示人工复核 | 是 |
| 内容 | 备注混排多字段（合同号 + 项目名 + 说明） | 由增强点按补充字段分别定义；无法分离时保留整段原文 | 是 |
| 内容 | 未配置增强点的老类型 | 行为与升级前逐字段一致 | 是 |
| 用户 | 非管理员查看 / 编辑增强点 | 只读；编辑需权限 | 待定（见 D-权限） |
| 状态 | 增强点改动时已有任务在跑 | 任务启动时取快照，运行中不切换 | 是 |
| 异常 | 增强点语法错误 / 提示词超长 | 降级到基础模板并告警，任务标 warning | 是 |
| 异常 | LLM 返回非 JSON | 走既有 JSON 修复 → 仍失败则降级并在 failures 留痕 | 是 |
| 权限 / 风控 | 增强点变更审计 | 记录操作人、改前 / 改后、时间 | 是 |

## 八、验收标准（可验证句）

1. 当增值税发票类型配置了备注增强点并重跑 OCR 时，该发票的 `extracted_fields` 应包含备注类字段，且值取自票面备注栏。
2. 当某单据备注栏为空时，该字段应为 `null` 且出现在 `low_confidence_fields`，而不是静默缺失。
3. 当未配置任何增强点时，同一文档的 OCR 结果应与升级前逐字段一致（回归不变）。
4. 当一次 OCR 任务完成时，`ocr_tasks.applied_config` 应记录本次使用的增强点与提示词版本。
5. 当把某增强点回退到上一版本后，后续识别应使用回退后的版本，且历史结果保留其原版本标记。
6. 当在 OCR 对照页对某处人工修正点击「沉淀为增强点」时，应生成**候选**且不自动生效，需人工确认后才影响后续识别。

### 9.1 关于 D3：评测集是什么，原来有没有

- **是什么**：一组固定的「样本 + 期望答案」（金标准）。每次改提示词 / 字段清单 / 后处理规则后自动重跑，输出**字段级准确率 / 召回率**和"哪些字段变好、哪些变坏"的差异清单。相当于给"识别质量"补上代码里 `tests/` 那套能力——没有它，"改完是不是更好"只能靠感觉（第五章的实测正说明了这点）。
- **原来没有**：仓库里没有任何评测集 / 金标准样本 / 字段级准确率的东西（全仓搜索 `评测集|金标准|样本集|准确率` 只命中本方案与 `file_classifier.py` 注释里引用的历史「PRD AC1 分类准确率 ≥ 90%」口径）。现有的只是：
  - `tests/`：代码级回归 + **冒烟测试**（`run_graph_rule_tests.py` 的 14 条图谱审查断言；`test_ocr_model.py` 会**真实调用** OCR，但只判断调用成功 + 文本长度，**没有期望字段值、不产出准确率**，固定样本目录缺失时回退到 `backend/uploads` 里的第一张图）——验的是"能不能跑通"，不是"抽得准不准"；
  - `document_types.sample_file_path` + `POST /api/doc-types/analyze-sample`：每个类型可留**一个样例**供 AI 分析类型/字段——这是评测集的雏形，扩成"每类型 N 个样例 + 期望字段值"即为评测集。
- **建议**：评测集放三期建；**一期就要求把每次人工修正留痕**（修正前值 / 修正后值 / 单据类型 / 字段名），三期建集时原料现成（对齐行业"用户反馈积累错误案例"的做法）。

### 9.2 关于 D5：既有机制是什么，建议怎么做

**既有机制**（`rule_parse_skill`，代码事实）：

- 实体 `RuleParseSkill`：`rule_set_id = NULL` 为系统内置（全局），非空为该规则集自定义；改元数据（启用/停用/优先级）直接改内置本体，改**内容**则自动生成"该规则集下的副本"（`parent_id` 指回内置，便于追溯）。
- 内容是一份"解析控制包"：`prompt_instructions`（追加到解析提示词纠偏）/ `field_mappings` / `defaults` / `validations` / `text_preprocessing` / `term_normalization` / `domain_context`。
- **版本**：仅当内容变化才 `version + 1`；启用/停用/改名不动版本。
- **注入**：规则导入时按规则集取已启用 Skill 合成 directive——`prompt_instructions` 进解析提示词，`field_mappings` / `defaults` / `term_normalization` 在入库前做后处理。
- **经验自动累积**：人工修正解析结果时，`learn_from_correction` 把差异写成 `[经验修正 YYYY-MM-DD] …` 指令，追加进规则集下的「经验修正（自动累积）」Skill（去重 + `version + 1`）。即**已经有一套"修正回流 → 沉淀 → 刷进提示词"的闭环，只是它服务规则解析，不服务 OCR**。

**建议：复用其治理模式，不把 OCR 增强点塞进 `rule_parse_skills` 表。** 理由：

1. 作用域键不同：Skill 挂 `rule_set`（客户）；按 D2，OCR 增强点挂**全局 + 单据类型**。混在一张表会让"改内置 → 建副本"的语义含混。
2. 注入点不同：Skill 注入的是**解析规则**的提示词；OCR 增强点注入的是**识图**提示词，且要带字段清单（`document_types.key_fields`）。
3. 生命周期不同：Skill 跟规则集走，增强点跟单据类型走；客户换规则集时增强点不该跟着变。

可直接沿用的三件：

- **版本语义**：只有内容变化才 `+1`，改启用状态不升版本；
- **内置 + 副本**：内置默认增强点不可删，改动生成副本（一期作用域为全局，可先简化为"全局一份 + 变更历史"）；
- **经验修正自动累积**：OCR 对照页的人工修正生成 `[经验修正 日期] 某类型某字段曾识别错误：…` 形式的候选指令，人工确认后进增强点（对应三期 FR-8）。
